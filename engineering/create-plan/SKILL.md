# 実装計画の作成

`create-plan <issue-or-task>` を入口に、個別実装で使う一時的な計画を作る。
計画は実装設計の契約だが、永続的な設計文書ではない。

## 前提情報の調査

次の repo-local 設定が存在すれば読む。

```text
docs/agents/engineering-flow.md
docs/agents/issue-tracker.md
docs/agents/domain.md
```

これらは任意の追加情報であり、存在しないことを停止条件にしない。
設定がなければ `AGENTS.md`、`CLAUDE.md`、リポジトリ内の関連文書、ユーザー入力から必要な規則と目標を特定する。

入力が issue identifier で、issue tracker 設定がある場合はその設定に従って取得する。
設定がなくても tracker を入力から一意に特定できる場合は取得してよい。
issue がない場合は、ユーザーのタスク説明を計画の入口として扱う。
参照された Design Doc、ADR、PRD と、判断に必要な関連コード・テスト・設定を読む。

repo-local flow を継続運用として保存したい場合だけ `setup-engineering-flow` を提案する。
今回の計画作成を設定の完了待ちで止めない。

## 手順

1. issue、タスク、またはユーザー入力から目標、対象範囲、完了条件、上流の設計判断を確認する。
2. コードベースを調査し、現状、既存 pattern、変更境界、検証方法を確認する。
3. 調査だけでは確定しない重要な設計判断があり、観察結果によって plan が変わりうる場合は、`prototype` を使って検証する。
   - 既存 code、test、文書で答えられる問い、単なる理解不足、局所的な実装詳細には使わない。
   - 技術的成立性には最小の単一 spike、代替案の判断には必要な数の比較案を選ぶ。
   - prototype が問いを解消できなければ成功扱いにせず、`grilling` へ戻る。
   - 作成と削除は[プロトタイプのライフサイクル](#プロトタイプのライフサイクル)に従う。
4. `grilling` を使い、共有理解に必要な問いを一度に一つずつ解消する。
   - なぜ必要か
   - 何を満たせば完成か
   - 壊してはいけない制約
   - 責務と interface の境界
   - 正しさを判定する振る舞い
5. 重要な未決定事項がなくなったら、リポジトリ固有のフローに設定されたディレクトリへ計画を作る。設定がなければ `plans/` を使う。
   - issue / task ID がある場合は `<task-id>-<short-slug>.md` にする。
   - task ID がない場合は `<short-slug>.md` にする。
   - 同じ task の plan が既にある場合は上書きせず、再開・置換・中止のどれかを確認する。
   - 計画のディレクトリや命名規則を `.gitignore` に追加しない。
6. 作成した計画が無視または追跡されておらず、未追跡ファイルとして可視であることを確認する。

   ```bash
   git check-ignore --no-index <plan-path>
   git ls-files --error-unmatch <plan-path>
   git status --short --untracked-files=all -- <plan-path>
   ```

   `git check-ignore` または `git ls-files` がパスを返した場合はライフサイクルの契約を満たさないため停止する。
   `git status` が `?? <plan-path>` を示さない場合も停止し、既存 rule / index の状態を報告する。
7. 計画を読み直し、別セッションの実装エージェントが追加の設計判断なしに実装と検証を行えることを確認する。
8. prototype を使った場合は、観察結果と設計判断が plan に残っていることを確認し、prototype 固有の file と diff を削除してから[プロトタイプのライフサイクル](#プロトタイプのライフサイクル)の清潔性判定を通す。
9. `review-plan`で計画を独立評価する。
   - `revise` findingは、要求とrepository contextから一意に直せる範囲でplanへ反映し、fresh reviewerで再reviewする。
   - `investigate` findingは、安全な調査やproofで解消できる場合は実行し、planへ反映して再reviewする。
   - `decision` の指摘、上流設計の変更、対象範囲の拡大、追加の権限が必要な場合は、自動で決めずユーザーへ一度に一つ質問する。
   - 同じfindingが再発する、finding同士が矛盾する、または修正の複雑性が低減するriskに見合わない場合はloopを止め、blockedとして報告する。
   - `ready`以外の結果で実装可能と表現しない。

## 計画の契約

標準の見出しは次の5つだけとする。

```md
# <title>

## 目的

## 現状

## 設計方針

## 完了条件

## スコープ外
```

参照、制約、変更対象、検証、採用しない案は、関係する章へ自然に書く。
タスク固有で必要なら、ロールバック、手作業、関連 issue などの見出しを追加してよい。
局所的な構文や意味のない逐次編集手順は固定しない。

## プロトタイプのライフサイクル

`prototype` は計画の判断材料であり、正式な実装差分ではない。
repository 内を含む、問いを適切に検証できる場所へ作成してよいが、次の境界を守る。

1. 作成前に `git status --short --untracked-files=all` と対象パスの差分を確認し、開始時からある追跡済みまたは未追跡のユーザー変更と、prototype が触るパスを記録する。
2. 開始時に変更のあるパスは編集しない。別のパス、専用 route、fixture、adapter など、prototype 由来の変更を分離できる足場を使う。
3. 変更のない既存パスを編集する場合は、開始時の基準を復元可能に保持し、prototype 由来の変更だけを除去できる境界を定める。新規パスは prototype の所有物として列挙する。
4. ユーザー変更と prototype の変更を安全に分離できなければ、そのパスを使う試作を中止して `grilling` へ戻る。別の検証方法でも重要判断を解消できない場合だけユーザーへ確認する。
5. 観察した事実と、それによって確定した判断を計画の該当章へ移す。
6. `review-plan` の前に prototype 固有のファイルと差分を削除する。削除はこのライフサイクルの完了操作であり、開始時からあるユーザー変更を戻さない。
7. 削除後に `git status --short --untracked-files=all` と対象パスの差分を開始時の記録と比較し、開始時からあるユーザー変更と未追跡の計画ファイル以外に prototype 由来の変更が残っていないことを確認する。

## 計画のライフサイクル

- 計画ファイルは作業中だけ存在する未追跡ファイルであり、一度も commit しない。
- 実装、検証、レビュー、修正が終わるまでは計画を保持する。
- 通常は完成した変更を最初の実装 commit としてまとめる。
- commit 時は計画の原文を commit body の固定 marker 内へ取り込み、その後に計画ファイルを削除する。
- 途中 commit が必要な場合は、最初の commit body に計画を取り込むが、ファイルは実装完了まで保持し、最後の commit 前に削除する。

```text
Implementation-Plan:

<plan 原文>

End-Implementation-Plan
```

## 安全上の制約

- 計画作成中に正式な実装差分を作らない。
- 判断用 prototype は[プロトタイプのライフサイクル](#プロトタイプのライフサイクル)の範囲でのみ作成する。
- 既存のユーザー変更を戻さない。
- 計画ファイルの commit、`.gitignore` への追加、tracker 更新、commit、push は行わない。

## 完了条件

- 計画ファイルの保存場所を報告した。
- 解消した重要判断と、参照した issue / 永続設計文書があれば報告した。
- 計画に実装を妨げる未解決事項がない。
- `review-plan`が`ready`を返し、採用した`blocker`が残っていない。
- 計画ファイルが無視または追跡されておらず、`git status` で未追跡として可視である。
- prototype を使った場合は、判断と根拠が計画に保存され、prototype 由来の変更がレビュー前に削除されている。
- 実装へ進めるかを報告した。
