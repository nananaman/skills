# TDD

外から観測できる振る舞いを、期待する理由で失敗するテストから実装する。
テストの命名、構造、fixture、mockの書き方は `test-writing-style` に従う。

## 検証する契約を選ぶ

対象の公開インターフェース、既存テストと実行方法を読み、今回変更する条件と期待結果を特定する。
既存テストで十分に守られている契約には重複テストを足さない。重要経路、境界条件、過去の不具合を優先する。

- 複数moduleの協調や永続化は、service / handler / usecaseなどの公開インターフェースを通した対象限定の結合テストを優先する。
- 純粋関数、変換、正規化、検証規則などは単体テストを使う。
- E2Eは主要フローやrouting、外部systemとの結合リスクを確認する必要がある場合に使う。

内部実装や値の写経ではなく、変更によって壊れ得る契約を検証する。

## Red → Green → Refactor

一つの振る舞いごとに次のサイクルを完了する。全機能分のテストや実装を先にまとめて書かない。

1. **Red**：公開契約を通して失敗するテストを書く。バグ修正では不具合を再現する。
2. 対象を絞って実行し、期待する理由で失敗することを確認する。環境不備による失敗をRedの証拠にしない。
3. **Green**：そのテストを通す最小の実装を書き、対象テストを実行する。実装に合わせて期待を緩めない。
4. **Refactor**：Greenを保って重複、命名、責務を整える。変更した範囲のテストを再実行する。
5. 必要な契約が残っている場合だけ次のサイクルへ進む。追加検証は、変更の影響や未解決の懸念から選ぶ。

動作変更では、Redを観測するまでGreenの実装へ進まない。
観測できなければ、許可範囲で環境を修復するか、同じ公開契約を確認できる対象限定テストを使う。それでも実行できない場合は、該当する実装だけを保留し、試した確認と不足する環境を報告する。

## 振る舞いを変えないリファクタリング

先に既存テストが守る範囲を確認する。安全網が十分ならそれを実行し、不足する場合だけ公開動作を固定する特性テストを追加する。
特性テストは最初からGreenでもよい。変更後に守るべき既存動作が確認できたことを根拠に進める。
安全網を実行できない場合は上記と同様に復旧・代替確認を試し、それに依存する変更を保留する。
リファクタリング中に動作変更が必要になった場合は、通常のRedから始める。

## 宣言的な変更

ユーザーがTDDを明示していない設定値・宣言的データ・skill・agent指示・文書だけの変更には、既存validator、schema、レビューなど成果物に合う検証を使う。
それらを解釈・評価する実行ロジックを変更する場合はTDDを適用する。
TDDの適用を求められた変更で別の検証を選ぶ場合は、選択理由と確認できる範囲を説明する。
