# TDD

実装前に外から観測できる契約を定義し、失敗するテストを確認してから最小実装へ進む。
この skill は TDD の進め方を制御する。個々のテストの命名、Arrange / Act / Assert、1 テスト 1 関心、mock / fake、文言固定を避ける判断は `test-writing-style` の観点を適用する。

## 使用条件

- 実行コードのロジック、状態遷移、データ変換、API・型・schemaの処理規則を変更するとき。
- 実行コードのリファクタリング前に既存の振る舞いを守れているか確認するとき。
- ユーザーが TDD、テスト駆動、test-first、red-green-refactor、失敗するテストからの実装を求めたとき。

使わない場面:

- ユーザーがTDDを明示していない、宣言的データ、設定値、policy entry、skill、agent instruction、文書だけの変更。
- テストコマンドを実行するだけのとき。
- CI 失敗原因を調査するだけのとき。

TDD を適用しない場合は、実装前または報告時に理由を 1 文で明示する。

例:

- allowlistへの項目追加だけで評価ロジックは変わらないため、validatorと代表的な境界確認に留める。
- skill本文だけの変更で実行コードは変わらないため、skill reviewで検証する。
- 既存の結合テストが同じ公開契約を既に守っているため、内部補助関数の単体テストは追加しない。

## 原則

- テストは実装詳細ではなく、公開インターフェースから観測できる動作と契約を検証する。
- 全テストを先に書かない。一つの動作ごとに `RED → GREEN → Refactor` を縦切りで進める。
- 動作変更を伴う場合は、RED を観測するまで GREEN の実装へ進まない。
- 動作変更を伴わないリファクタリングでは、RED のサイクルではなく安全網の観測として扱う。
- GREEN までは現在のテストを通す最小実装に留める。
- Refactor は GREEN 後だけ行い、各リファクタリング手順の後に関連テストを実行する。
- 重要経路、複雑な分岐、過去バグ、境界条件を優先し、既に守られている契約の重複テストを増やさない。

## 手順

1. **既存の入口とテストを読む**
   - 変更対象の公開インターフェース、利用者から見える動作、API 契約を確認する。
   - 同じ層と同じ機能周辺の既存テストを読み、テストコマンドと補助関数を把握する。
   - 既存テストが今回守りたい契約を既に十分に守っているか確認する。

2. **テスト対象にする契約を 1 つ選ぶ**
   - 実装手順ではなく、外から観測できる条件と期待結果として書く。
   - 追加テストが必要な契約だけを選ぶ。文言や表示データを写経するだけのテストは書かない。
   - 複数の動作がある場合も、まず一つだけ選ぶ。

3. **RED：失敗するテストを書く**
   - 動作変更を伴う場合は、公開インターフェース、利用者から見える動作、API 契約を通して失敗させる。
   - バグ修正では、現在の不具合を再現する退行テストを書く。
   - 動作変更を伴わないリファクタリングは「リファクタリング」節に従い、既存動作の安全網を先に確認する。
   - テストを書くときは `test-writing-style` の観点を適用する。

4. **RED を実行して確認する**
   - 動作変更を伴う場合は、対象を絞ったテストを実行し、期待した理由で失敗することを確認する。
   - RED を観測できない場合、GREEN 実装へ進んではならない。
   - 観測できない場合は、実行内容、期待した失敗、実際の停止理由、環境を整える解決案、より小さな対象限定テストへ切り替えられるかを報告して止める。

5. **GREEN: 最小実装を書く**
   - 現在失敗しているテストを通すために必要な最小変更だけを行う。
   - 将来の動作を先取りしない。
   - 内部構造に合わせてテストを緩めたり、失敗理由を変えたりしない。

6. **GREEN を確認する**
   - 対象を絞ったテストが成功することを確認する。
   - 必要に応じて近接する関連テストも実行する。

7. **Refactor**
   - GREEN を保ったまま、重複、命名、責務分離、module boundary を整える。
   - リファクタリング中に動作変更が必要になったら、通常の RED サイクルに戻る。

8. **次の動作へ進む**
   - まだ必要な契約が残っている場合だけ、次の一つの動作について RED から繰り返す。

## テスト範囲の選択

公開契約を守れる最小のテストレベルを選ぶ。

1. 既存の結合テストまたは契約テストが同じ契約を十分に守っているなら、新規テストを追加しない。
2. 複数モジュールの協調、永続化、service、handler、usecase の主要動作は、公開インターフェースを通した対象限定の結合テストを優先する。
3. 純粋関数、変換、正規化、検証規則、境界値、期間計算、複雑な分岐は単体テストを使う。
4. E2E は主要フロー、routing、browser / native / external system との結合リスクが高い場合だけ使う。

サーバーやバックエンドでは、service、handler、usecase、repository などの公開インターフェースを通した結合テストを優先する。既存の結合テストが同じ契約を守っている場合、内部関数や非公開の補助関数に単体テストを重複追加しない。

## 宣言的な変更とエージェント向け変更

ユーザーがTDDを明示していない場合、宣言的データ、設定値、policy entry、skill、agent instruction、文書だけの変更にはTDDを使わない。
各値をテストへ写経せず、既存の検証処理、schema 検査、代表的な境界確認、または対象成果物のレビュー手順で検証する。
ただし、それらを解釈・評価する実装ロジックを変更する場合はTDDを使う。

## リファクタリング

リファクタリングでは、先に既存テストが対象の公開動作を守っているか確認する。

- 十分なら、新規テストは追加せず、既存テストを安全網として使う。
- 不足しているなら、実装変更前に特性テストを追加して既存動作を固定する。
- 非公開の補助関数や内部構造を固定する特性テストは避ける。
- 特性テストは既存挙動を固定するため、最初から GREEN になることがある。この場合は RED ではなく安全網の観測を完了条件にする。
- 追加または既存の安全網を実行できない場合は、実行内容、停止理由、環境を整える解決案を報告して止める。
- リファクタリング中に動作変更が必要になった場合は、通常の RED サイクルに戻る。

## モックを使う境界

mock / fake の詳細な判断は `test-writing-style` の外部依存隔離と副作用検証の観点に従う。

## 各サイクルの確認事項

- 今回守る契約を一文で説明できるか。
- 新規テストは本当に必要か。既存テストと重複していないか。
- 公開インターフェース、利用者から見える動作、API 契約を通して検証しているか。
- 文言や表示データそのものを固定していないか。
- 動作変更では対象を絞ったテストの RED を期待した理由で観測したか。
- リファクタリングでは既存動作の安全網を GREEN として観測したか。
- GREEN 実装は現在のテストを通す最小量か。
- GREEN 前に refactor していないか。
- test-writing-style の観点を満たしているか。
