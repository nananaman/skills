# Design Doc の仕上げ

Design Doc draft を、設計の採否を判断でき、task 分割に進める文書に仕上げる。
対象は `TODO(draft)` が解消された draft とし、構造は [Design Doc template](../draft-design-doc/assets/design-doc-template.md)、文章は `japanese-tech-writing` に従う。

## 設計の確定

関連コード・文書と repo-local の前提を調べ、`TODO(polish)` と設計上の矛盾を解消する。
合意済みの判断を使う。未決定の案は根拠を比較して推奨案を示し、必要なユーザー判断を `grilling` で確認する。
採用案の仕組み・成立条件・利点・限界を本文に反映し、実際に検討した不採用案と理由を `検討した案` に残す。

重要な成立条件を調査だけで判断できなければ、最小の試作やテストで確かめる。
試作は既存のユーザー変更と分離し、観測結果を文書へ残してから、試作由来の変更だけを除去する。安全に除去できない状態では仕上げを完了扱いにしない。

## 完了条件

- 目的、対象外、背景・制約、用語が明確である。
- 採用案と根拠、実装判断に十分な詳細設計がある。状態を持つ設計では状態遷移を示す。
- 既知の限界と、セキュリティ・プライバシー・負荷やコスト・信頼性・開発運用への影響を評価している。考慮不要な項目にも理由がある。
- 設計の未決定事項と TODO がなく、task に分割できる。

条件を満たした文書を `状態: Polished` として保存し、場所・重要な判断・検証結果を報告する。未解決ならその内容を示す。
