# コードの簡素化

完成に近いコード差分から、既存機構で置き換えられる実装、不要な抽象化、状態、分岐、読みにくい制御フローを除き、振る舞いを変えない完成差分を返す。

## 契約

修正対象は、今回の作業に属すると確認できるパスだけにする。
範囲は、ユーザー指定、実装セッションが保持する変更パス、作業ツリーの未コミット差分、基準ブランチとの差分の順で判断する。
今回の作業に属するか不明なユーザーの変更は、参考として読めるが編集しない。

通常の実装フローから呼ばれた場合は、呼び出し元が示した関連検証の成功結果を確認してから、簡素化を適用する必要があるか判断する。
直接依頼された場合は、対象差分、守るべき公開された振る舞いと契約、実行可能な安全網を特定し、修正前に検証が成功することを確認する。

差分のリスクに応じて、次から必要な確認項目を選ぶ。

- コードベースに既にあるユーティリティ、パターン、ライブラリの再利用
- 不要な抽象化、状態、分岐、代替処理、重複
- 制御フローの読みやすさ、責務の置き場所と抽象度
- 追加または変更されたテストが、公開契約に対して固有の検出能力を持つか
- 重複計算や不要なメモリ確保など、局所的で明白な無駄

行数の削減、書き方の好み、根拠のないYAGNI、別の設計への大幅な書き換え、今回と無関係な整理は指摘にしない。
計測や実行環境についての判断が必要な性能最適化は適用せず、別の作業候補として報告する。

同じ公開契約を既存テストが十分に守っている場合は、重複テスト、内部実装を固定するテスト、値を写しただけのテスト、検証対象より複雑なテスト用抽象化を簡素化候補にする。
テストを削除または統合する前に、そのテストだけが守る正常系、異常系、境界条件、過去の不具合がないことを確認する。
固有の回帰防止能力を失う変更は採用しない。

小さい差分は、担当エージェントが一度確認すればよい。
複数の構成要素をまたぐ探索など、独立した調査によって根拠が明らかに強まる場合だけレビュー担当を追加する。
候補が競合する場合は、多数決や行数ではなく、振る舞い、リポジトリの規約、保守コスト、検証可能性を根拠に採否を決める。

## 終了状態

### `skipped`（対象外）

今回の作業に属し、検証に成功している差分について、コード整理の対象でない場合、またはフォーマッター、リンター、TDDの局所的なリファクタリングで十分な場合に選ぶ。
ファイルを変更せず、対象、検証結果、対象外とした理由を返す。

### `completed`（完了）

採用した指摘のうち、振る舞いを変えず、対象範囲内で検証できるものだけ修正する。
既存の安全網が不十分なら、`tdd`のリファクタリング契約に従い、公開された現在の振る舞いを固定する最小限のテストを先に追加する。

修正後に関連テスト、静的解析、型検査などを再実行する。
検証が成功し、対象範囲内に未処理の採用済み指摘がなければ完了する。

### `blocked`（続行不能）

次のいずれかでは安全に完了したと表現せず停止する。

- 必要な安全網を成功させられない、または修正後の検証に失敗した
- 振る舞いの変更、要求の追加、権限の追加が必要になった
- 変更が今回の作業に属するか安全に判断できない

修正前ならファイルを変更しない。
修正後なら適用した変更を勝手に破棄せず、作業ツリーに残す。
変更パス、続行できない理由、失敗した検証、未検証の範囲、次に必要な最小限の作業を返し、完成差分の`review-diff-code`へ進めない。

## 報告

次を報告する。

- 対象差分と`skipped`、`completed`、`blocked`のいずれかの終了状態
- 確認した項目
- 採用、棄却、適用した指摘と根拠
- 実行した検証と結果
- 残るリスクまたは次に必要な作業

簡素化で差分が変わった場合、後続の`review-diff-code`はその完成差分を評価する。
レビュー指摘の修正によって新しい非自明な複雑性が生じた場合だけ、簡素化の必要性を再評価する。
簡素化とレビューを無条件には繰り返さない。
