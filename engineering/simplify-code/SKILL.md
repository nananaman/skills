# コードの簡素化

既存機構で置き換えられる実装、不要な抽象化・状態・分岐を除き、振る舞いを変えずに保守しやすくする。

## 対象と判断

今回の作業に属すると確認できる変更だけを対象にする。ユーザー指定、実装セッションの変更範囲、作業ツリーや基準branchとの差分から特定し、所有が不明な変更は編集しない。
通常の実装フローでは呼び出し元の検証結果を利用する。直接の依頼では、公開契約を守る安全網を修正前に確認する。

次から今回の差分に必要なものを調べる。

- 既存のutility、pattern、libraryで代替できる処理。
- 不要な抽象化、状態、分岐、重複と、読みにくい制御フロー。
- 責務の置き場所と、局所的で明白な無駄。
- 同じ公開契約を重複して検証するテストや、内部実装だけを固定するテスト。

行数や好みだけの変更、根拠のないYAGNI、別設計への書き換え、無関係な整理は行わない。
テストの削除・統合では、そのテストだけが守る正常系・異常系・境界条件・過去の不具合がないか確認する。
計測が必要な性能最適化は別作業に分ける。

## 適用と検証

整理の利益が小さい、またはformatterやTDDの局所的なリファクタリングで十分なら、変更なしで終えてよい。
小さい差分は主担当が確認し、独立した調査が根拠を強める場合だけ担当を追加する。

安全網が不足する場合は `tdd` のリファクタリング手順に従う。
変更後は影響したテスト・静的検査を実行し、対応可能な指摘を解消する。後続のレビュー範囲は `implement` のリスク基準に従い、このskillから独立レビューを無条件に要求しない。

必要な検証を実行できない場合は、許可範囲で復旧・同じ契約の確認を試す。それでも確認できない変更は保留する。
振る舞いの変更や追加の権限が必要な場合も、その部分だけを保留する。適用済みの変更を勝手に破棄せず、確認できた範囲と未検証部分を報告する。

## 結果

`skipped`（変更不要）、`completed`（簡素化と検証が完了）、`blocked`（必要な変更・検証を完了できない）を区別する。
変更内容と検証結果を簡潔に返し、棄却候補や全チェック項目の台帳は判断に必要な場合だけ示す。
レビュー指摘の修正で新しい非自明な複雑性が生じた場合だけ、簡素化の必要性を再評価する。
