# 簡潔性の判断基準

要求と既存の契約を満たすうえで、複雑性が必要かを判断する。
実装者は探索・修正に、独立した専門レビュー担当は指摘の根拠に使う。

- 既存のutility、pattern、libraryで代替できる処理を再実装していないか。
- 不要な抽象化、拡張点、設定、状態、分岐、互換層、過度な防御処理がないか。
- 重複、責務の混在、読みにくい制御フローが変更や検証を難しくしていないか。
- テストが同じ契約を重複して検証したり、過度なfixture・mockや内部実装への依存を持ち込んだりしていないか。

実行時のバグがなくても、要求・利用箇所・既存機構から不要と確認できる保守負担は改善対象にする。
対象箇所、不要と判断する根拠、具体的な負担、契約を保つ最小の単純化を説明できることを基準にする。
行数や好みだけの変更、根拠のないYAGNI、無関係な再設計は行わない。
必要な抽象化、安全境界、互換性を短文化のために失わせない。
テストを削除・統合する際は、そのテストだけが守る正常系・異常系・境界条件・過去の不具合を失わないことを確認する。
