# 実装

依頼された成果を実装し、必要な検証、レビュー、採用指摘の修正まで終える。
目標・対象範囲・完了条件を基準に進め、無関係な改善を加えない。

## 設計と検証

公開 API・型・schema の契約を明確にする。静的に検査できる規則は linter や formatter に置く。
暫定実装の TODO には追跡先と解消条件を残す。
成果物に合う検証で完了条件を確かめ、指定された KPI やカバレッジ目標は達成まで取り組む。

必要な専門 skill を使う。

- 実行可能な振る舞いの変更：`tdd`
- テストの追加・変更：`test-writing-style`
- agent skill・AGENTS.md・tool 指示の作成・改善：`skill-workbench`

## 簡素化

実装中や、コードの簡素化を直接依頼された場合は、[簡潔性の判断基準](references/simplicity.md)で不要な複雑性を探し、利益がある箇所を直す。
今回の依頼に属すると確認できる範囲だけを扱い、公開契約と振る舞いを保つ。
実装中に十分確認できた箇所は探索を繰り返さず、整理不要なら変更なしで終えてよい。
簡素化のためだけに別担当や独立した工程を設けない。

通常は実装中の検証結果を使う。直接のリファクタリング依頼では、変更前に安全網を確認し、不足があれば `tdd` のリファクタリング手順を使う。
修正後は影響したテスト・静的検査を行う。実行不能なら許可範囲で復旧・代替確認を試し、確認できない変更は保留する。
適用済みの変更を勝手に破棄せず、未検証部分を報告する。

## レビュー範囲の選択

完成差分を要求・退行・検証不足の観点で確認する。
AIが実装・変更した意味のあるコード差分には、`review-diff-code` による専門担当の契約・簡潔性レビューと、blind担当の敵対的検証を必ず行う。
実装者が行った簡素化は独立レビューの代わりにしない。
誤字・空白・formatterだけの変更や、差分のない調査には独立コードレビューを要求しない。

skill のみの変更は `skill-workbench` で評価する。実行コードを含む場合はコードレビューも行う。
その他の設定・agent指示等は変更の影響に応じて確認し、重大な影響や検証不足があれば独立レビューを加える。
既に同じ差分を評価済みなら結果を使う。
採用した指摘を修正し、修正箇所と影響範囲を確認する。修正のたびに全探索・全レビューを最初から繰り返さない。

## 完了

依頼された成果が成立し、必要な検証・レビューが成功し、採用した指摘が解消されていれば完了する。
成果、検証結果、残る制約を報告する。必須の確認ができない範囲は未完了として示す。
