# 実装

依頼された変更を実装し、検証、簡素化の判断、完成差分のレビューを経て、対応可能な指摘が残っていない状態まで進める。

## 対象

コード、設定、テスト、schema、依存関係、agent 指示を作成または変更する実装タスクで使う。
調査、診断、計画、レビューだけの依頼、文書だけの編集、commit、push、PR 作成だけの依頼では使わない。

## 契約

着手前に次を一意に定める。

- 利用者から見える目標と対象範囲
- 自律実行できる操作と、追加確認が必要な権限境界
- 実際の成果物に対して判定できる完了条件

結果や変更範囲を大きく左右しない不明点は、安全な仮定を明示して進める。
ユーザーの判断、追加権限、外部への書き込み、破壊的操作、または実質的な対象範囲の拡大が必要になった場合は、その操作へ進まず確認する。
安全な調査後も判定可能な完了条件を定義できない場合は、不足している最小限の情報またはユーザーの判断を求めて停止する。
作業中に見つけた無関係な問題や、将来のためだけの改善は対象へ加えない。

公開 API、型、設定 schema など、利用側との境界を明確に定義する。
静的に検査できる規則は、agent 指示ではなく、その環境の linter や formatter に実装する。
意図的な未完了実装や暫定対応を残す場合は追跡 issue または task を先に用意し、コード内 TODO には追跡先と、何をいつ実装、削除、置換するかを書く。

## 実装フロー

1. 目標、対象範囲、完了条件を確認する。
2. 変更対象に応じて専門 skill を適用する。
   - 実行可能な振る舞いの変更：`tdd`
   - テストの追加または変更：`test-writing-style`
   - agent skill の作成または改善：`skill-workbench`
   - agent 向け prompt の改善：`improve-agent-prompt`
3. 依頼された変更を実装する。
4. 完了条件に対応するテスト、静的検査、型検査、または実動作確認を行う。
   KPI やカバレッジ目標が指定された場合は、達成するまで検証と改善を続ける。
5. 検証済みのコード差分について、`simplify-code`を適用する必要があるか判断する。
6. 簡素化した場合は、影響する検証を再実行する。
7. 簡素化後の完成差分を、変更種別に対応するレビュー skill で確認する。
8. 採用した対応可能な指摘がある場合は、依頼範囲内で修正して再検証し、完成差分を再レビューする。
9. 「完了と停止」の条件をすべて満たし、対応可能な指摘がなくなった時点で完了を報告する。

## 完成差分のレビュー

実装済みコードを含む場合、`review-diff-code`の前に、検証済みの差分へ`simplify-code`を適用する必要があるか判断する。
追加の簡素化が費用に見合わなければ、`skipped`は正常な結果である。
簡素化で差分が変わった場合は、関連する検証を再実行し、その変更を含む完成差分をレビューする。

レビュー指摘の修正によって新しい非自明な複雑性が生じた場合だけ、再レビューの前に`simplify-code`の必要性を再評価する。
簡素化とレビューを理由なく繰り返さない。

レビューには、変更種別に対応する skill を使う。

- agent skill の変更：`skill-workbench`の差分レビューまたは全体レビュー
- コード、設定、テスト、schema、依存関係、その他の agent 指示：`review-diff-code`

差分全体が、振る舞いと契約に影響しないコメント、誤字、空白、formatter のみの変更であることを確認できる場合は、レビューを省略してよい。
必要なレビューが`partial_failure`または`failed`になった場合は完了せず、原因、評価できなかった範囲、次に必要な最小の作業を報告して停止する。

## 完了と停止

次をすべて満たした場合だけ、実装を完了したと報告する。

- 依頼された成果が成立している。
- 必要な検証が成功している。
- 実装済みコードを含む場合は、`simplify-code`の適用要否を判断している。
- 完成差分に必要なレビューで、すべてのレビュー担当が成功しているか、レビューの省略条件を満たしている。
- 採用した対応可能な指摘が残っていない。

完了条件を満たす前に、実装完了を報告したり、commit、push、PR 作成へ進む提案をしたり、ユーザーへ作業を引き渡したりしない。

ユーザーの判断、追加権限、対象範囲の拡大、または実行できない必須検証が必要になった場合は停止する。
停止時は、理由、完了済みの範囲、未検証事項、残るリスク、次に必要な最小の作業を報告する。

完了時は、変更した成果、実行した検証、簡素化の判断、レビュー結果、残る未検証事項を簡潔に報告する。
