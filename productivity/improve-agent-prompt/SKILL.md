# Agent 向け指示の改善

ユーザーの成果を妨げる指示を特定し、必要な制約を残して削除・限定・統合する。
既存の手順、停止条件、出力項目は、それ自体を保存する目的にはしない。

## 対象と根拠

対象 prompt と、実際に重なる上位指示・skill・tool の説明を確認する。依頼が診断・提案だけなら報告に留め、編集の依頼なら変更と検証まで進める。
対象が取得できない場合は、その不足を報告する。取得できた範囲の診断は続け、未知の本文を推測して書き換えない。

モデル固有の判断は GPT-6 Astra を基準にする。他モデルが明示された場合はその指定を保つ。
同じ会話で根拠を取得済みなら再取得せず、未確認のモデル固有判断には `openai-docs` で対象モデルの公式ガイドを確認する。
Astra の判断材料と反例は [references/contract-review.md](references/contract-review.md) にある。関係する論点を参照し、全項目を作業や出力の必須欄にしない。

## 改善の判断

- ユーザーが要求した成果、明示値、業務・安全・権限の制約、後続の利用者やツールが依存する形式を守る。既存の「必須」「停止」「承認」には、その必要性を示す根拠があるかを問う。
- 不要な確認や停止には、会話内の許可を使えているか、判断待ちの部分だけを保留できるかを確認する。依頼の範囲を拡大して自律性を得ようとしない。
- 手順の追加より、競合する指示の削除、適用条件の限定、共通規則の集約を優先する。領域固有の落とし穴や不可逆な操作の境界は根拠を残す。
- 検証とレビューは変更の影響に合わせる。既存の必須手順も見直すが、ユーザーやプロジェクトが求める検証を無断で省かない。
- 文体や進捗、委譲の既定値は上位指示との重複を避け、対象固有の調整だけを書く。細かい言い換え例や固定人数を全作業へ適用しない。
- 同じ原因が複数ファイルにまたがるなら、一貫して解消する範囲を変更する。一文ずつの修正に拘って、矛盾を残さない。

各指摘は、対象箇所、余計な停止・作業または誤動作が生じる条件、影響、変更の方向を説明できるものにする。
実行記録による事実と、本文から推論した失敗の可能性を区別する。既存の指示に書かれていることだけを、維持する根拠にしない。

## 検証と報告

変更後の指示を、問題の起きる入力と、制約を残すべき反例に当てて確認する。skill のレビューでは `skill-workbench` が本文の過剰制約も評価するため、保存対象表を別途完成させることを前提にしない。
静的な確認で残る不確実性がある場合は、その判断を確かめる動作確認を選ぶ。実行型評価を行うなら、変更前後で同じ入力・モデル・実行条件を使う。
未実行の評価を成功扱いにせず、短文化だけで品質・速度の向上を実証したと表現しない。

結果、重要な変更と根拠、実施した確認、残る不確実性を返す。契約表や定型の章立ては、判断に必要な場合だけ使う。
