# Prompt の契約レビュー

この参照資料は診断と改善の共通診断で読む。
各項目を prompt の見出しに変換するためではなく、agent の判断に必要な契約が存在するか検査するために使う。

## 契約の対応表

| 要素 | 確認事項 | 保持または追加する条件 |
| --- | --- | --- |
| 成果 | ユーザーに見える到達状態は何か | 手順はあるが完成状態が曖昧 |
| 成功条件 | 終了前に何が真である必要があるか | 早すぎる完了判定が起きうる |
| 制約 | 安全、権限、業務、対象範囲の境界は何か | 誤った行動や範囲拡大を防ぐ |
| 根拠と前提条件 | 判断または行動の前に必要な根拠は何か | 探索や検証を飛ばせる |
| 権限境界 | 自律実行と確認要求の境界はどこか | 過剰確認または無断の行動が起きる |
| Tool | 何を、いつ、どの結果やエラーを見て使うか | 振り分けが前提情報に依存する |
| 進捗と状態 | 長時間作業で何を伝え、段階をいつ移るか | 無言の待機、過剰な実況、段階の飛び越し、再開時の重複が起きる |
| 前提情報の配置 | 契約をどの層へ置き、いつ取得するか | 常時読み込む情報、重複、精度の低い文章を減らせる |
| 出力 | 必須の内容、形式、長さ、検証結果は何か | 後続の利用者が期待する形がある |
| 停止と代替 | 再試行、代替、質問、回答の保留、終了はいつか | 反復、推測、早期終了が起きる |

## 診断項目

### 保存対象

- 明示された利用者向けの値、成果物、長さ、構造、文書形式、事実に関する主張を優先して残す。
- 安全と権限の条件、必須の根拠、出力項目、検証、失敗時の処理を削除候補から外す。
- prompt の階層では同じ規則の正式な出典を特定する。
- 編集、書き換え、要約では、指定された成果物、長さ、構造、ジャンル、事実関係を維持し、要求されていない主張や章を追加しない境界が必要か確認する。創作や発想展開には機械的に適用しない。

### 削減

削除または統合の候補：

- 同じ規則の言い換え。
- 挙動を変えない文体や手順の指示。
- 挙動を変えない例。
- agent が安定して実行できる挙動の逐語的手順。
- 作業と無関係な tool または tool の説明。

残す対象：

- 利用者に見える成果。
- 成功条件と停止条件。
- 安全、権限、業務、根拠に関する制約。
- 前提情報に依存する tool の振り分け。
- 必須の出力と検証。

### 矛盾

- 同じ状況で「先に確認する」と「自律的に続行する」が競合していないか。
- 簡潔さの指示によって必須内容が欠けないか。
- tool の呼び出し回数の最小化が、根拠、計算、引用、検証より優先されていないか。
- 人格や文体の規則が、事実の正確さや成果物の保持と競合していないか。
- prompt の階層の上位と下位に、異なる既定値や禁止がないか。

矛盾は指示を追加して覆い隠さない。
適用条件、優先順位、権限境界のいずれかを一箇所で明示する。

### 自律性と承認

- 回答、説明、レビュー、診断、計画は、読み取り専用の調査と報告を既定にする。
- 変更、構築、修正は、依頼範囲内のローカルな変更と非破壊的な検証を許可する。
- 外部への書き込み、破壊的操作、購入や高額な実行、実質的な対象範囲の拡大には、明示的な許可境界を置く。
- 安全なローカル操作を明示したら、同じ承認規則を複数箇所で繰り返さない。
- 承認を求める前に、変更予定の成果物やファイルと行動を列挙する。承認後に別の成果物、追加の行動、実質的に異なる対象範囲が必要と分かった場合は、その範囲へ進まず再承認を求める。

### Tool と根拠

- 前提情報の取得、探索、検証を最終操作より前に置く。
- 独立した読み取りは並列化できるが、前の結果で次が変わる呼び出しは逐次にする。
- 空、不完全、不自然に狭い結果には、一つか二つの有効な代替手段を定義する。
- 根拠が見つからないことを、事実として存在しないことに変換しない。
- 引用が必要なら、裏付ける対象、十分な根拠、欠落時の挙動を定義する。
- 複数の情報源を統合する場合は、取得した情報源が直接裏付ける事実、agent の推論、情報源間の不一致を区別できるか確認する。
- retrieval budget は固定回数だけで表さず、追加取得が必要な欠落と、十分な根拠が得られた終了条件で判断できるようにする。

### 長時間作業の進捗と状態

複数段階または複数の tool 呼び出しを伴い、利用者に待機が発生する prompt で確認する。

- 最初の tool 呼び出し前に、これから行う作業を短く伝えるか確認する。
- 進捗更新は主要な段階の開始または計画を変える発見に絞り、通常の tool 呼び出しを逐一実況しない。
- 更新には、具体的に得られた結果と次に行うことを含める。
- 調査、設計、実装、レビュー、外部調整などを区別する必要がある場合は、現在の段階、移行条件、移行に必要な許可を判断できるようにする。
- 再開時は完了済み作業を繰り返さず、新しい指示で目的や優先順位が変わった場合は古い状態へ固執しない。

短い回答、単一の tool 呼び出し、待機が利用者へ露出しない処理には、この契約を機械的に追加しない。
上位 prompt または runtime が同じ進捗契約を持つ場合は重複させず、正式な出典へ寄せる。

### 前提情報の配置

各指示は、内容だけでなく正式な配置先を確認する。

- 製品全体の役割と不変条件は system prompt または agent 向け指示に置く。
- repository 固有で、コードやファイルシステムから発見できない注意点は AGENTS.md 系の前提情報に置く。
- 作業や分岐に依存する手順と詳細は skill と参照資料へ分け、必要時だけ取得できる導線を残す。
- セッションをまたぐ事実や好みは、利用可能なら記憶機能に置く。
- コード、テスト、schema、型、評価基準、試作画面、リンターのほうが高精度に表せる契約は、文章で重複管理しない。
- 作業と無関係なターンでも常時読み込む必要がない情報を、上位の prompt に置かない。
- 同じ規則が複数の層にある場合は正式な出典を一つにし、必要なら他方には導線だけを置く。

prompt 以外の変更が依頼範囲外なら実装せず、移動先と必要な別作業を指摘として報告する。

### Tool のインターフェース

- tool の能力と利用条件が、名前、引数、型、列挙値から判別できるか確認する。
- 必須項目と任意項目、排他的な操作、状態遷移を文章の例だけに依存させない。
- 戻り値が次の判断に必要な状態を返し、エラーと正常な空結果を区別できるか確認する。
- tool の説明は、schema から分からない利用条件、重要な戻り値、失敗時の挙動に絞る。
- prompt 内の例がインターフェースの不足を補っているだけなら、インターフェースの改善を優先して提案する。

### 例と高精度な参照資料

例は、schema で表現できない意味上の境界、固有の好み、紛らわしい反例、観測済みの失敗を伝える場合に残す。
通常手順の再現、tool の schema の言い換え、偶然選んだ一つの探索経路の固定にしかならない例は削除候補にする。

文章による説明よりコード、テスト、schema、型、評価基準、試作画面、正準実装のほうが正確な場合は、高精度な参照資料への置換を提案する。

### 出力と簡潔さ

- 結論、必須の事実、判断、重大な留保、次の行動を優先して残す。
- 短くするときは、導入、反復、一般的な安心材料、任意の背景説明から削る。
- 人格は語調を、協働の様式は質問、仮定、自律性、検証、不確実性の扱いを制御する。
- 広すぎる分類名ではなく、実際の書き方を短く指定する。

### 終端状態

- 変更、提案、指摘が 0 件でも正常終了できるようにする。
- 再利用可能な根拠なし、完全重複、ユーザーによる却下、必要情報の未取得、変更不要をそれぞれ終端状態として扱えるか確認する。
- 何も行わない場合は、理由と確認した範囲を報告し、成果物を作るためだけの提案を追加しない。
- 必要な入力がなければ最小の不足情報を一度求め、それでも取得できなければ未完了理由を報告して停止する。

### 検証の完全性

- 必須のテスト、レビュー、描画、外部 tool、別の agent による確認を実行できない場合、別の確認を同等の代替として扱わない。
- 未実施の検証、実行できない理由、残る危険、次に必要な確認を報告する。
- 必須検証が未実施、失敗、または対処可能な指摘を残している場合、検証済みまたは完了済みと表現しない。
- 任意の検証と完了条件を区別し、任意の検査ができないことだけで正常な作業を止めない。
- 実行型評価では運用中の prompt を基準にし、同じ代表例と表明で変更後と比較する。
- 一度に変える変数を一つにし、退行の原因を追跡できるようにする。
- token、待ち時間、費用、tool 呼び出しの削減は、既存の品質基準を満たした場合だけ改善と数える。

## 変更ごとの確認

各変更について確認する。

1. どの観測可能な失敗または契約の欠落を直すか。
2. 保存対象のどの項目に影響するか。
3. 削除または統合で解決できず、新しい指示が必要か。
4. 静的検査で判定できるか、代表例による評価が必要か。
5. ほかの失敗要因と分離できているか。
6. 承認が必要な場合、許可される成果物、ファイル、行動が一意か。
7. 変更なしの終了と、必須検証不能時の終了を正しく表現できるか。
8. 指示の配置先と取得時点は適切か。
9. 例や文章をインターフェースまたは高精度な参照資料で置き換えられないか。

答えられない変更は適用しない。
