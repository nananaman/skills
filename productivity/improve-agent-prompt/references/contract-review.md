# Astra 向けの指示レビュー

GPT-6 Astra の [公式ガイド](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices) を根拠にした判断材料（2026-09-08確認）。
[skillsとpromptの見直しに関する記事](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)（2026-09-12確認）は、起動条件の精度、条件付きの参照、固定手順と停止条件の見直しを勧める。
公式資料が述べるモデル傾向と、以下のローカルな改善方針を区別する。対象固有の効果は変更前後の評価で確かめる。

## モデル傾向と見直す指示

公式ガイドは、Astra が skill や AGENTS.md の指示に敏感で、確認のために早く止まる場合があることを述べる。また、小変更への過剰検証、詳しい書式付き回答、委譲頻度を調整対象に挙げている。
長い指示を一律に削る根拠ではない。問題のある指示と適用条件を特定し、次の観点から変更を選ぶ。

| 症状 | 確認する指示 | 改善の方向 |
| --- | --- | --- |
| 許可済みの作業で止まる | 再承認、全文preview、作業種別だけでの確認要求 | 依頼・合意を使い、未許可の操作だけを確認する |
| 入力の一部不足で全作業を止める | setup、metadata、補助資料の無条件な前提化 | 取得済みの根拠から成果物を作り、依存部分だけ保留する |
| 小変更が長いworkflowになる | 固定人数のレビュー、全件検査、形式だけのtest | 影響範囲と検証不足から必要な確認を選ぶ |
| 文書が長い、同じ説明が反復する | 多数の必須欄、毎回の台帳・除外理由・実況 | 利用者の判断に必要な結果と根拠に絞る |
| 目的のない委譲が増える／独立評価まで省く | 時間短縮だけの委譲推奨、無条件の禁止・必須化 | 単独実行を既定とし、会話履歴の分離や独立した視点など具体的な目的がある場合に委譲する |
| 改善のたびに規則が増える | 既存契約の無条件保存、失敗ごとの例の追記 | 原因となる規則の削除・限定・統合を候補にする |

## 保存する根拠を問う

保存すべき要求は、現在のユーザー意図、業務・安全・権限の境界、外部の利用者やツールの依存から決める。
それを実現するために過去に選んだ手順や停止条件は、改善対象である。

- 「必須」という語だけで削除不可にしない。その検査が防ぐ失敗と、他の手段で確認できるかを調べる。
- 自律性を理由に、ユーザーの明示した都度確認や不可逆な操作の制約を緩めない。
- 出力を読むツールがいるならschemaや形式を保持する。人間向けの報告項目は、判断に必要かを見直す。
- 共通規則は実際に読み込まれる上位指示へ集約する。別環境で単独利用するskillなら、必要な前提が失われないことを確認する。
- 同じ方針を別の表現で繰り返すより、競合する原文の適用範囲を直す。

## 反例で確かめる

変更に関係する例だけを選ぶ。例の数や手順の消化を完了条件にしない。

| 問題の起きる入力 | 期待する変化 | 残すべき境界 |
| --- | --- | --- |
| 合意済みの案を文書へ反映して | 再承認なしに依頼された文書を更新する | 提案だけなら編集せず、新しい要求判断は確認する |
| 設定が未整備のrepoでタスク分解して | 入力から分解案を作る | 不明な作成先へ勝手に書き込まない |
| 局所的で可逆な設定変更、対象検証は成功 | 主担当の確認で終えられる | 認可・データ損失などのリスクや明示のレビュー要求を見落とさない |
| 必須レビュー規則そのものを見直して | 必要性を評価し、削除・限定を提案できる | 明示的な品質・権限要件を無断で撤去しない |

## 評価の限界

本文の静的読解は、矛盾・不要な依存・明示条件の変化を確認できる。
Astra の実際の選択や完了率、費用、所要時間の改善は、同じ入力と実行条件での比較が必要である。
品質の合格条件を維持したうえで不要な質問・読み込み・検証・報告が減ったかを見る。単発の成功や行数削減から一般化しない。
