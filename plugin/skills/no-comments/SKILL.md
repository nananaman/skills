# コメントに頼らないコード

説明のためのコードコメントを追加しない。コメントで分かりにくさや回避策を正当化する代わりに、コメントが不要になる設計へ直す。テストや検証scriptにも適用する。

## 対象を絞る

指定されたfileやdiffを対象にする。指定がなければ、今回の変更と理解に必要な周辺を読む。無関係な既存コメントの一括削除や、依頼外の全面改修をしない。
生成物や第三者コードは直接書き換えず、変更権限のある生成元・呼出側で対応する。

## 意図と制約をコードへ移す

- 処理の説明、段落見出し、変更履歴、TODO、無効化したコードを残さない。docstringや空のhelperへ説明を移すだけで済ませない。
- 意味・単位・条件が分かる名前にし、責務の混在、隠れた状態、不要な分岐や回避策を解消する。説明のためだけの分割や抽象化を増やさない。
- 「削除禁止」「この順番が必要」などの制約は呼出先と実際の挙動まで確認し、型、公開API、実行時検証、振る舞いのテストなどで成立させてから説明コメントを外す。
- lintや型検査の抑制で不具合を隠さない。ルールと対象箇所を調べ、正しさ・安全性に関わる問題は原因を直す。
- テストでは条件と期待結果をテスト名・ケース名・入力値・assertionで示す。Arrange / Act / Assertは処理の順序と空行で表し、区切りや検証観点のコメントを付けない。

## 削除で壊してはいけないもの

次は説明用の逃げ道にせず、必要性を確認できる最小限を維持する。

- 著作権、ライセンスなどの法的表示。
- shebang、build tag、codegen指示など、ツールが解釈し動作に必要なディレクティブ。抑制指示はこの理由だけで保護せず、対象ルールが誤検知か書式上の制約で、正しさを損なわないことを確認する。
- 公開APIの利用者や生成ドキュメントが依存する契約。必要なAPI docは保ち、実装の実況や同じ内容の重複を加えない。
- 変更できない外部依存・platform・protocolの制約で、コードでは表しきれない事実。現行の仕様や実行経路で裏付け、必要ならissueやRFCを示す。自分たちのコードの都合を外部制約と呼ばない。

必要性が不明な契約やディレクティブは推測で消さない。調べても確かめられなければ該当箇所を残し、未解決として報告する。

## 変更を確かめる

コメントが伝えていた意味・制約を失っていないか、外から見える振る舞いと必要なbuild・lint・型検査で確認する。コメント数の減少だけを成功としない。
根本修正が依頼範囲を越える場合は、制約を失わせる削除や抑制の除去を止め、許可範囲内の変更を完成させる。残る問題と必要な追加作業を示す。
結果には設計上の変更、実施した検証、維持した例外とその根拠、未解決事項を必要な範囲で示す。
