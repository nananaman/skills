# Notes の検証マップ例

架空の Notes アプリに対する形式例。`notes` と `control-notes` はこのスキルに同梱していない。実際に生成するときは対象で確認した操作手段・ラベル・コマンドへ置き換える。
操作前にこの一覧を読み、該当する機能ファイルを選ぶ。

## 共通の前提

- 検証用インスタンスを `http://127.0.0.1:4173` で起動する。
- `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID` のような試行別データを使う。並列実行ではポートも分ける。
- タイトル `Quarterly plan`、本文 `Draft budget` のノートと、`Grocery list` を seed する。
- `control-notes` と `notes` が PATH にあり、`control-notes doctor` で URL・データディレクトリ・ビルドが期待どおりと確認する。
- この試行が起動したインスタンス以外は操作しない。

## 操作と証拠

各手順は、個別の前提がない限り共通の初期状態から始める。安定した ARIA role と name を優先し、コマンド中のラベル・フラグはそのまま使う。
ブラウザは `control-notes browser`、CLI は `control-notes cli -- <command>` を使う。
証拠はリポジトリ外の試行別ディレクトリ `$EVIDENCE_DIR` へ保存し、一時データとは分離する。
UI は操作記録と、その結果が出ている時点の ARIA snapshot・スクリーンショットを残す。CLI はコマンド、stdout、stderr、終了コードを残す。
変更は別の利用者向け読み取り経路で永続化も確かめる。証拠に機能 ID と入口を添える。
操作後は seed を復元するが、証拠は片付けで消さない。
到達できない入口は試したコマンドと不足する前提を報告し、別経路の成功で検証済みにしない。

## 機能ファイルの形式

H1 と利用者視点の説明に続け、`サブ機能`、`利用者から見た入口`、`<操作手段> での操作`、`注意点` の四つの H2 を使う。
内部実装ではなく、入口、安定した操作対象、前提、コマンド、観測できる結果を書く。
