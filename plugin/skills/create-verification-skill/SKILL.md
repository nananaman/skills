# プロジェクト専用の検証スキルを作る

実アプリを起動し、利用者と同じ操作で機能を確かめ、証拠を保存できるスキルを `.agents/skills/verify-<app>/` に作る。
対象を初めて扱う次のエージェントが、作業途中でも単独で使える内容にする。本文と機能マップは日本語で書き、実際のコマンド・識別子・画面ラベルは改変しない。

## リポジトリから調べる

次の情報をコード・README・開発コマンド・既存テストから確認し、観測できない必須事項だけ利用者に聞く。

- **操作面**：Web、CLI/TUI、デスクトップ、API、モバイル、ライブラリなど、利用者が触る入口。複数なら主な対象と対象外を分ける。
- **起動**：既存の開発コマンドを優先し、ポート、環境変数、認証、初期データを確認する。
- **操作手段**：既存の Playwright/Cypress、PTY、expect、HTTP、デバッグ接続などを先に探す。なければ利用可能なブラウザ操作、PTY/tmux、HTTP クライアント等を選ぶ。Cursor や特定の browser tool を前提にしない。
- **観測**：画面、端末出力、レスポンス、ログ、終了コード、保存状態など、証拠にできるもの。
- **分離**：ポート、データディレクトリ、プロファイルで並列実行を分離できるか。共有インスタンスしか使えないなら明記し、利用者のセッションを勝手に二重操作しない。

ビルド・起動が壊れていれば原因を特定する。依頼範囲内で直せるものは直し、無関係な修正は広げず報告する。未確認の起動手順を検証済みとして生成しない。
検証に必要な仮ディレクトリや設定を補う場合は検証用の補助物と明記し、片付け対象に含める。

## 検証スキルを生成する

`.agents/skills/verify-<app>/SKILL.md` に `name: verify-<app>` と、アプリ名・操作面・使用条件を表す `description` の YAML frontmatter を付ける。
既存の同名スキルがあれば内容を確認して必要箇所だけ更新する。以下は調査結果から具体化し、実在しないコマンドや未解決のプレースホルダーを残さない。

- **起動**：正確なコマンド、必要な migration・seed、利用可能と判断する条件、終了方法。空の検証データから使える状態まで到達させる。ポート応答や DB の health check だけで初期化完了としない。短命の CLI/TUI はビルドを済ませ、各操作を分離した PTY 等で起動する。
- **診断**：読み取り専用で「操作してよいインスタンスか」を確かめる方法。プロセス、ビルド、ポート所有者、認証状態など、対象に必要な識別を含める。不調時はまずこれを使う。
- **操作**：このリポジトリで実在するコマンド・セレクターを使った手順。座標や Tab 順より、ARIA 名、安定した属性、プロンプト、ルートを優先する。
- **証拠**：保存先と証明条件。内部 setter やテスト専用入口ではなく実際の利用者経路を操作し、操作と結果を対にして記録する。画面だけでなくファイルや永続化などの副作用も確認する。mock は本番でも外部システムが分離される境界に限る。dry-run/test モードも名前を信じず、実際に省く処理と発生するファイル・通信等を確認する。外部への送信・課金などは検証依頼から自動的に許可されたと解釈しない。
- **片付け**：自分が起動した PID・セッション・一時データだけを終了・削除する。プロセス名で一括終了しない。証拠は消さず、一時データとは別の保存先を示す。
- **補助スクリプト**：必要なものだけ同梱し、実行可能にして本文に呼び出し方を書く。読者が実装を逆解析しないと使えない補助物にしない。

## 機能マップを作る

`.agents/skills/verify-<app>/features/README.md` と、確認できた主要な利用者向け機能ごとのファイルを作る。初期版は主要 3〜5 機能を目安とし、存在しない機能を数合わせで追加しない。
[機能マップの例](references/feature-map-example/README.md)を形式の参考にする。例は架空の Notes アプリであり、そのコマンドを対象プロジェクトへそのままコピーしない。

README に共通の前提・証拠の保存方針・機能一覧を書く。各機能ファイルは H1 と利用者視点の説明に続けて、次の四つの H2 を使う。

1. `サブ機能`：短い ID と、確かめる振る舞い。
2. `利用者から見た入口`：画面、ショートカット、CLI など、その機能への各入口。
3. `<操作手段> での操作`：前提条件に続けて、利用者の操作・正確なコマンド・観測できる期待結果を対にする。
4. `注意点`：前提不足、非同期処理、実行を無効にする落とし穴など。

seed に必要な前提がなければその経路は失敗または未検証として理由を記録し、通すために検証条件を弱めない。
複数入口を載せた場合、便利な一つを通しただけで全入口を検証済みにしない。

## 生成した手順を試す

生成した手順のとおりに起動、診断、機能マップの一機能の操作、証拠保存、片付けを一通り実行する。全機能の実行はここでの完了条件ではない。
失敗時もその試行の片付けを行い、残ったプロセスやポートを次の試行に持ち越さない。修正後に再実行し、片付け後も指定先に証拠が残ることを確かめる。

実行できない場合は生成物を未検証の草案と明記し、阻害要因と未確認の手順を報告する。代替環境だけで試した場合は、実対象との差と代替環境だけで済ませた準備を列挙し、実対象も検証済みとはしない。
成果の報告には生成先、試した機能と入口、証拠の場所、未検証範囲を含める。

## 更新時

アプリが変わったら機能マップと操作手順も合わせて更新する。保守用スキルを案内する場合は、その環境に実在するものだけを示す。定期実行の設定や install は生成作業に含めない。
