# PRDとDesign Doc

PRDは作る価値と要求を、Design Docは実現方法と設計判断を説明する。
対象repoの既存形式と保存先を優先し、指定がなければ次のテンプレートを使う。
両方を一律に作らず、依頼された文書だけを扱う。

| 文書 | テンプレート | 主な内容 | 保存先の既定 |
| --- | --- | --- | --- |
| PRD | [PRD template](../../assets/prd-template.md) | 対象ユーザー、課題と根拠、提供価値、利用の流れ、範囲、提供上の制約、成功条件、採用案、受け入れ条件 | `docs/prd/<short-slug>.md` |
| Design Doc | [Design Doc template](../../assets/design-doc-template.md) | 技術的な問題、背景と制約、用語、採用案と理由、詳細設計、限界、影響、比較した案 | `docs/design/<short-slug>.md` |

## テンプレートを使う

関連する要求、コード、設計文書から、既知の判断と未決定事項を分ける。
PRDを実現する設計ならそのPRDを参照し、技術改善から始める設計に新しいPRDの作成を要求しない。
読者、用途、求める判断は、目的や概要など既存の節へ反映する。

同梱テンプレートの基本の見出しと記述意図を保ち、title、date、PRD参照などのplaceholderを実値へ置き換える。
PRD参照がなければ、その旨を書く。
比較する意味のある案だけを置き、空の案を形式のために追加しない。
採用済みの判断は本文へ反映し、実際に検討した不採用案と理由を「検討した案」へ残す。
採用案の価値、仕組み、成立条件、利点と欠点を本文へ移す際に落とさない。

`TODO(draft)`は問題、要求、制約、比較案などの基本項目、`TODO(polish)`は採用案と詳細、受け入れ条件や影響を具体化する記入位置を示す。
これらは文書の状態を区別する目印であり、別のskillや担当への引渡しを要求するものではない。

草案の依頼では基本項目を埋め、`状態: Draft`として未決定事項と残る具体化を示す。
基本項目も確定できない場合は不足を示し、草案完成と報告しない。
仕上げまで依頼された場合は採用判断と根拠を本文へ反映し、TODOと記入用コメントを解消する。
必要な判断が得られなければDraftのまま、その判断事項を返す。

## 文書ごとの確認

- PRDでは、誰のどの問題を解くか、作るものと対象外、成功条件と受け入れ条件を外から確認できるかを見る。画面が関係する場合は画面と遷移を示し、実装方法はDesign Docへ分ける。
- Design Docでは、採用案の境界、責務、依存と処理の流れ、実装判断に必要な詳細と既知の限界を示す。複数component、重要な処理順、永続状態には、それぞれ概要図、sequence diagram、state diagramを使う。
- Design Docの影響項目は、セキュリティ、プライバシー、負荷とコスト、信頼性、開発と運用から関係するものを残す。非該当の判断が重要な場合だけ理由を書き、それ以外の空の影響節は除く。
- 重要な成立条件が資料だけでは判断できない場合は、今回許可された調査や検証の結果を使い、未検証の成立を断定しない。

内容、構造、表現のレビューで見つけた問題を解消し、未決定事項がなく、要求や設計の判断に使える文書を`状態: Polished`とする。
保存先、重要な判断、検証結果と未確認事項を報告する。
