# テストの資源と完了

テストが取得する資源、変更する共有状態、待つべき完了を確認するときに読む。
I/Oを行わないparserへ渡す固定URLやpathの文字列は、取得した資源ではない。

## 資源の確保と復元

- port番号自体が検証対象でないserverは、`listen(0)`などでOSにportを割り当てさせ、listen完了後に取得したaddressを使う。空き番号を調べてsocketを閉じ、後から同じ番号へbindする方法は競合を防げない。
- 一時directoryは`mkdtemp`などでテストごとに作り、DBやsocketにも独立した名前を使う。同じfile内の直列化だけでは、別workerやprocessとの共有を解消できない。
- 環境変数、作業directory、clock、global mockを変更する場合は、元の値と未設定の違いを保持して復元する。変更範囲は必要な呼出しに絞り、instanceへ依存を渡せるなら共有状態の変更を避ける。

## 準備と終了を観測する

準備完了は、ready通知、状態、所有するpromiseなどで待つ。
一定時間のsleepを準備完了の証拠にしない。
競合が論点ならbarrierなどで操作の重なりを作る。timeoutは待機を打ち切る条件であり、正しい順序を作る手段ではない。

後処理では新しい仕事を止め、登録を解除し、子processのexitやserverのcloseなど、所有する作業の終了を待つ。
`abort()`や`kill()`を呼んだだけで、終了したと判断しない。
assertionや準備の失敗でも後処理が走るようにし、遅れて届く処理が別のテストを変更しないことを確かめる。

## 不安定なテストの修正

再試行、timeoutの延長、全体の直列化で通ったことだけを修正の根拠にしない。
待っている状態と資源の所有者を特定し、元の実装で対象の失敗が起き、修正後は同じ条件で起きないことを確認する。
別processとの共有が原因なら同じ共有条件で確認し、時刻が検証対象なら制御可能なclockを使う。
実APIの一時的な失敗など、外部サービスの再試行方針に従う場合は、その境界と理由を区別する。
