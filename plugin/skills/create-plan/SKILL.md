# 実装計画の作成

issue・task・ユーザー説明から、別セッションの担当が実装と検証に進める一時計画を作る。

## 判断と根拠

依頼された作業が、ユーザーの達成したい状態にどうつながるかを確かめ、今回の目標、制約、変更境界を定める。
ユーザー指定、対象repoのAGENTS.md、関連する設計・issueから前提と保存先を確認する。専用のフロー設定は前提にしない。
関連する要求、設計文書、コードに加え、判断に必要な一次資料、実物、測定結果を調べる。
重要な前提を確かめる具体的な手法を選び、完了条件を、要求に基づく期待結果と実物の観察、測定、テストなどで作成者の説明から独立して判定できる形にする。
他分野の手法も、重要な前提や見落としを確かめる使い道があれば検討し、判断に役立つ根拠が得られたものだけ計画へ反映する。
合意済みの目的と明示制約を守り、範囲を変える案は、許可済みの作業と分けて提案する。
調査の深さは判断への影響に合わせ、小さな修正は短く済ませる。
調査で解けない判断は `grilling` で一問ずつ確認する。
調査だけでは判断できず、観察結果が方針を変えうる場合は、下記のライフサイクルに従って必要最小限の試作や実験を行う。

## 計画の契約

標準構造は次とし、必要な参照と制約、判断を変えた根拠、採用した手法、完了を判定する検査を該当章へ書く。
検討した観点の一覧は出力せず、小さな変更は各章を短くまとめる。
実装担当が安全に決められる局所的な編集手順は固定しない。

```md
# <title>

## 目的

## 現状

## 設計方針

## 完了条件

## スコープ外
```

保存先は repo の設定に従い、なければ `plans/<task-id>-<short-slug>.md` とする。task ID がなければ省く。
既存の同一 task の計画は再開・置換の意図を確認する。
計画は Git に無視・追跡されない未追跡ファイルとして保持し、`git check-ignore --no-index`、`git ls-files`、`git status --short` で確かめる。

## プロトタイプのライフサイクル

試作前の status と差分を記録し、既存のユーザー変更と分離できる場所を使う。
既存の変更があるパスは編集しない。変更のない既存パスを使う場合も、開始時へ復元できるようにする。
観測した事実と判断を計画へ残し、レビュー前に試作由来の差分・新規ファイルだけを除去する。
開始時の状態と比較し、ユーザー変更と未追跡の計画以外に試作の残留がないことを確認する。

## レビューと完了

`review-plan` で独立評価し、`revise` は修正、`investigate` は追加調査、`decision` はユーザー確認で解消する。
修正確認は `review-plan` に従い、収束しない指摘は無理に解消扱いにしない。

未追跡の計画に重要な未決定事項がなく、試作の除去が確認でき、レビューが `ready` なら完了する。
計画の場所、重要な判断、実装に進めるかを報告する。満たせない条件は未完了として示す。
計画作成の依頼だけでは正式な実装・tracker 更新・commit・push に進まない。

## 計画の保持

計画は実装・検証・指摘修正が終わるまで保持する。
ユーザーが追跡を依頼しない限り commit せず、自動削除もしない。
永続的に残す判断が必要なら、依頼された成果物へ必要な内容を記録する。
