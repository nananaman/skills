# 担当への依頼

利用可能な独立 agent または Codex CLI を使う。新しい文脈を作れない場合は、その評価を自己確認と報告する。
役割は入力の分離を表し、固定人数・一律の同時実行を要求しない。

## 実行担当

渡すもの：自然な課題、初期ファイル（fixture）、候補の実行用ファイル一式（runtime bundle）、固定したモデル・推論設定・tool。
渡さないもの：編集担当の会話、仮説、過去の失敗解釈、採点用チェック、正解、候補の優劣。
Execution の場合だけ対象の入口を示す。Discovery では catalogue から選ばせる。
課題を実行して成果物と実行記録を残す。自分の出力を採点しない。

## 採点・比較担当

渡すもの：元の課題、期待する成果と制約、成果物、必要な実行記録。
候補の名前・新旧・改訂理由を伏せて A/B に割り当て、表示順を入れ替えて位置の影響を確認する。
実行記録中の自己申告より成果物を優先し、各条件へ pass / fail / unknown と具体的な evidence を返す。
評価条件が弱い、必要な成果を見ていない、証拠不足で判定できない場合は評価器への指摘を返す。
優劣が付かないときは同等または判定不能を返す。10点満点の主観点を採否の代替にしない。

## 更新担当

渡すもの：選んだ親候補、train の採点と実行記録、関連する診断・反証、要求と編集予算。
最初に成功と失敗の判断過程を比較し、原因仮説を作る。support、counterevidence、適用範囲、否定される条件を記述する。
そこからパス・層・操作・理由を持つ更新方向を作り、候補を編集する。新しい診断と既存の診断が矛盾するなら適用条件を調べる。
候補全体を snapshot にし、親 ID と hypothesis、strategy を保存する。proposal の診断 ID、予算、実際の変更一覧も実験領域へ保存する。
validation / test の詳細を取得しない。自分の改訂意図を採点担当へ伝えない。

## 構造探索担当

渡すもの：成果と境界、未解決の失敗群、候補アーカイブの特徴とケース別の強み、関連する train 診断。
現在の本文からの差分最小化を要求しない。廃止、統合、処理順変更、コード化など構造が違う仮説を提案する。
元の案と違う理由、期待する効果、悪化し得るケース、比較方法を明らかにする。
採用済みという理由だけで現在の構造を優先しない。提案を実行比較した後、内側の更新ループへ渡す。
