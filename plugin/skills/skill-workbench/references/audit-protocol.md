# Skill 一覧の監査

複数skillを使ったとき、ユーザーの成果に対して余計な停止・作業・読み込みが生じる経路を調べる。
各ファイルの長さや分類だけで、肥大化の有無と優先順位を決めない。

## 対象の確認

manifestとskillの正本を確認する。運用時の不整合を調べる場合だけ、読み込まれる上位指示や展開物も照合する。
監査だけの依頼では変更・installを行わない。取得できない対象は未確認として、根拠のある範囲の監査を続ける。

まずdescription、本文の構成、参照先から、調べるべき経路を選ぶ。
起動語だけでなく、同じ成果物、承認・検証の連鎖、共通規則、負荷の報告を手がかりにする。
全skillを毎回精読する必要はないが、結論を出す経路は本文と必要な参照先で裏付ける。

## 重点

- 正しく起動しても、許可済みの依頼を再承認やsetup待ちで止める経路。
- 小変更が固定人数のレビューや同じ検証の繰り返しへ広がる経路。
- 必須検証・停止規則・出力形式を、既存という理由だけで削除候補から外す改善手順。
- 上位では省略できる手順が、下位skillでは無条件になる経路。
- 同じ依頼で起動条件が競合する、または必要なskillが見つからない導線。
- 同じ方針をAGENTS.md、本文、README、参照資料に重複して管理する構成。
- 常時表示されるdescription、通常時の必読資料、実行時のtool・質問・報告が必要以上に多い構成。
- 一つのrepoや一度の失敗を、グローバル規則へ一般化している箇所。

skill固有の不可逆操作やデータ損失を防ぐ規則は、単に長いことを理由に削除しない。
本文が短くても参照連鎖が重ければ問題になり、操作マニュアルが長くても必要な箇所だけを読むなら、それだけでは問題にしない。

## 優先順位

重大度は [レビュー手順](review-protocol.md) の影響基準に従う。
完了不能・権限逸脱・重大な成果の破れを先に扱い、次に頻繁な不要確認や検証、最後に局所的な冗長さを見る。
過剰制約でも、通常の依頼を止めるならhighになり得る。起動条件の競合を無条件に最優先しない。

各問題は、自然な依頼、実際に適用される指示、そこで起きる停止や余分な作業、必要な修正範囲で説明する。
独立した問題群を作業担当へ委譲する場合も、主担当が対象本文で指摘を検証する。分類や多数決だけで採用しない。

## 報告

確認した範囲と正本、根拠のある指摘、推奨する対応順、未確認事項を返す。
削除・限定・統合・配置変更・現状維持から、問題を解消できる対応を選ぶ。指摘の数や新規skillの数を成果にしない。
単なる文字数集計と、実際の読み込み・実行費用の測定を区別する。
