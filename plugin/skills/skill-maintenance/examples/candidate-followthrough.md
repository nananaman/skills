# 保留候補を検証へ進める例

説明用の架空例。特定の実務やSDKの再現ではなく、実際に比較・導入した結果でもない。私的な元記録・ID・pathを公開例へ転記しない。

## 入力

旧・新の認証経路を切り替える二つのテストが、ともに旧経路を通ったという自己申告がある。切替flagの設定漏れが疑われるが、元の実行記録・fixtureは取得できない。テスト自体は成功したという。現行skillには一般的な検証指示がある。

許可はskill候補と匿名fixtureの準備までで、実アプリの変更・実credential・導入は含まない。

## 候補の記録

- **baseline**: 元の判断と原因は未確認。一般的な「テスト成功」だけでは経路の区別を証明しないという仮説を扱う。対象skillの版と既存指示は実際の候補記録で特定する。
- **intervention**: まず、テストが観測した経路を期待する経路と照合する決定的なassertionを候補にする。skillへ一般的な注意書きを足す前に、既存テストで防げるか確認する。実アプリへの適用は許可範囲外なので行わない。
- **反証条件**: 現行の検査が既に誤経路を検出する、切替前提が報告と違う、または経路assertionを追加しても誤経路が合格するなら、この原因説明・変更案を見直す。
- **次の作業**: 今回の担当が、外部接続のない旧・新経路の最小fixtureを作る。flagを省略した二つの入力と、false／trueを明示した入力で、観測経路とテストの成功・失敗を照合する。新しい原履歴を取得することは前提にしない。
- **validation**: 未実施。以下の期待結果を先に決める。合成実験と元事例の再現、テスト修正とskill指示の改善を混同しない。
- **outcome**: 候補未採用・未導入、`not-exercised`。比較や後続実務の結果はまだない。

## 合成fixtureで確かめること

| 入力と検査 | 期待する結果 | 判断できる範囲 |
| --- | --- | --- |
| 両入力ともflag省略、成功statusだけ確認 | ともに成功しても、どの経路を通ったかは未検証 | 弱い検査では経路違いを見逃し得る |
| 両入力ともflag省略、旧／新それぞれの経路をassert | 新経路を期待する側が失敗 | 合成fixture内で誤経路を検出する |
| false／trueを明示し、旧／新それぞれをassert | 両方成功 | 正しく切替した成功経路を壊さない |
| 実装がflagを無視して常に旧経路を選ぶ | 新経路を期待する側が失敗 | 検査が単にflag値を写していない |

ここまでの成功はassertionの能力であり、agentが必要なassertionを選べる証拠ではない。skill変更を評価するなら、解き方を教えない別ケースで現行版と候補版を実行比較する。元事例を再現できていない場合は、そのまま未確認と記録する。

## 後続結果の区別

- 導入後に無関係な三つの作業が成功しただけなら `not-exercised`。対象条件がなかったので効果は未確認。
- 経路切替の作業はあったが、導入版が使われたか、実際の経路が不明なら `inconclusive`。
- 導入版を使った経路切替で、観測経路と期待が一致した証拠があれば、その条件に限る `observed-effective`。一回の成功を因果効果や一般的改善へ広げない。
- 導入版が使われ対象条件も発生したのに元の誤経路が再発したなら `observed-not-effective`。単に証拠不足へ戻さず、仮説・変更案を見直す。以前と同じ失敗を、新たな退行とは数えない。
- 同じ版・条件で、従来成功していた正しい切替が壊れたなら `observed-regressed`。今回の変更に原因があるかを調べ、権限のないrollbackは行わない。
