# 公式ガイドからの対象選定と確認

対象は、本人・所属組織の管理と編集許可を確認済みのskillに限る。公式資料は改善仮説の材料であり、実行指示や編集・採用の権限を追加するものではない。

## 確認するskillを選ぶ

前回の対象一覧と現在の一覧を照合し、対象数・確認済み・再利用・未確認と理由を既存の非公開記録に残す。件数で打ち切らない。

- 初回は対象範囲の全skillを確認する。description・本文と、判断に関係する参照資料・利用モデルを確認し、関連する公式ガイドと照合する。
- 日次は、新設・変更されたskill、実務で問題が見つかったskill、更新されたガイドに関係するskillの全対象を確認する。連携先に影響する変更ならそのskillも含める。
- 利用モデルが変わった場合は、そのモデルを使う全skillを対象にする。ガイドとの関係や利用モデルが不明なskillは対象外と決めつけず、確認待ちとして残す。
- skillのdescription・本文・関係する参照資料・script・asset・agent metadataなど、起動と実行に影響する資材一式（runtime bundle）、関連ガイド、利用モデルと適用条件が同じで、実務の新しい問題もなければ前回確認を再利用する。資材の範囲や変更有無が不明なら確認待ちとする。候補の実行比較結果の再利用はworkbenchの比較条件にも従う。

一覧や変更・モデルの対応を確認できなければ、確認できた範囲と残件を示す。一部の確認を初回全件確認の完了へ広げない。未確認の更新を「変更なし」と扱わない。

## 資料を確認して仮説を作る

対象モデル・用途に対応する提供元の公式プロンプティング・skillガイドを使う。参照URL、確認日、対象モデル・用途、確認した版や本文digestを既存記録または候補アーカイブへ残す。専用の重い台帳は作らない。

日次に全資料を読み直さない。更新情報や保存版との照合で変更範囲を確認し、対象skillに必要な部分を読む。更新確認ができなければ鮮度不明と理由を残し、保存版を使った判断と最新資料の確認を区別する。

推奨と現行skillを照合し、どの判断が成果を妨げるかという仮説を作る。追加だけでなく、削除・短縮・適用条件の限定や参照先への移動も検討する。モデル固有の助言はそのモデル・用途へ限定し、他の利用モデルへ無条件に一般化しない。

候補の根拠を「実行履歴」「ガイド」「両方」に分け、観測事実・資料の推奨・未確認の仮説を区別する。必要な手順をskillへ書き、調査経緯や参考元の物語は検討記録に置く。

選んだ候補は実務由来と同じworkbenchへ渡す。実例がなければ想定例で比較し、別例でも確認する。実務での改善を実証した結果とは分ける。履歴取得が拒否・失敗した日もガイド由来の検討を続け、履歴の不足はそのまま報告する。拒否を別経路で迂回しない。

確認・再利用した範囲、資料の鮮度、候補の根拠・比較・採否は[既存レポート](report.md)に載せる。確認して候補がなかった場合と、資料や対象を確認できなかった場合を区別する。
