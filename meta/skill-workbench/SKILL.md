# 実行結果から skill を改善する

ユーザーの成果を改善するために、指示・参照資料・script・設定を更新する。既存の skill の維持を目的にしない。
効果を検証するときは「実行 → 診断 → 編集 → 検証」を繰り返し、保存した過去の候補から別の構造も探索する。

## 依頼と成果を確かめる

- 作成・改善の依頼では、下記の経路を選び、許可された編集と必要な確認、成果物の引き渡しまで進める。
- 設計相談・改善提案では、根拠と比較すべき候補を示す。編集はしない。
- 差分・全体レビューでは、[レビュー手順](references/review-protocol.md)で確認し、指摘を返す。
- 一覧の監査では、[監査手順](references/audit-protocol.md)で起動競合・連鎖・廃止候補を調べる。

ユーザーの成果、維持すべき要求・権限境界、今回変えてよい範囲を明らかにする。既存の手順や「必須」という文言から正解を作らない。

| 依頼・状況 | 進め方と完了条件 |
| --- | --- |
| 誤字、リンク、宣言的な整合性の修正 | 修正を既存 validator とレビューで確認し、「反映と報告」へ進む。評価準備・更新ループ・候補アーカイブは省略する |
| 新規作成 | [設計原則](references/design-principles.md)を使い、用途・起動条件・必要な知識から初期案を作る。実行可能なら skill なしとの比較へ進み、不可能なら下記の扱いで引き渡す |
| 既存 skill の挙動・性能改善 | 以下の評価準備と更新ループで候補を比較する。改善を実証したと述べるには実行比較の根拠が必要 |
| 評価環境・再現ケースが不足 | 診断と許可された編集、可能な静的確認を進め、「評価できない場合」の成果物と終了状態を使う |

## 評価できない場合

正本へ編集を反映する許可と、改善効果の実証を分ける。
新規作成や具体的な変更が許可され、要求への適合を静的に確認できる範囲は、指定された正本へ反映し、効果は未検証と報告して編集依頼を完了する。
例えば社内 MCP を使う skill の作成では、接続環境がなくても提供済みの仕様から本文を作成できる。実際の接続・動作確認は未実施とする。
評価合格が反映の条件である場合、または必要な要求・権限境界を満たすか確認できない場合は、正本への反映を保留し、候補を正本外へ保存して保存先・不足する確認を報告する。
評価や動作確認自体が依頼された成果に含まれるなら、その部分は未完了と示す。環境整備を依頼範囲へ自動追加せず、無関係な作業まで停止しない。

## 改善の準備

実行比較を行う場合は[評価と更新の手順](references/eval-loop.md)を読み、成果で判定できるケースと比較条件を先に定める。
コード基盤を使うときは[実験データと CLI](references/experiment-contract.md)を読む。新規作成や配置の判断には[設計原則](references/design-principles.md)を使う。

1. 実際の依頼・実行記録から失敗と成功の事例を集める。原因の解釈と観測事実を分ける。
2. 開発用、候補選択用、最終確認用のケースを分け、モデル・推論設定・tool・上位指示・初期ファイル（fixture）・評価の版を固定する。
3. 現行版を候補として保存する。新規なら skill なしを比較対象にする。既存でも追加価値が疑わしいなら skill なしを含める。
4. 評価実行の予算と終了条件を決める。予算不足は未検証であり、成功とは扱わない。

## 内側の更新ループ

1. 候補を、編集担当の会話を継承しない実行担当へ渡し、開発用ケースを実行する。
2. 独立した採点で成果物・実行記録と期待条件を照合する。可能なら決定的な検査を使い、弱い評価項目も指摘する。
3. 更新担当は成功と失敗を対比し、失敗を生んだ判断、根拠、反証、適用範囲を診断する。そこから追加・削除・置換・移動という更新方向を作る。
4. 関係する過去の診断を取り出し、再発・反証と照合する。これを momentum とする。反復された仮説を無条件の規則へ昇格させない。
5. 編集担当は更新方向を metadata・本文・参照資料・script・設定へ適用する。今回検証する診断の数と編集範囲を先に絞り、実際の差分がその範囲に収まるか確認する。
6. 別の検証ケースで親候補と比較し、改善・退行・変化なし・判定不能をケース別に記録する。

診断担当・編集担当は同一でもよい。採点と匿名比較には、改訂意図や期待する勝者を渡さない独立した文脈を使う。
各役への入力は[担当への依頼](references/agent-tasks.md)にある。役の数だけ同時起動する必要はない。

## 外側の構造探索

原因が不明、同じ失敗が再発、または同じ方向の編集で改善が止まった場合は、最新候補への追記を続けない。
候補アーカイブから、ケース別に強い候補、構造が異なる候補、未探索の枝を選び直す。
廃止・最小化・統合・責務や処理順の変更・scriptへの移行を候補にする。言い換えだけを多様性と数えない。

構造変更には内側の小さな編集予算をそのまま適用せず、変更する責務と検証範囲を定めた別候補を作る。
複数候補の知見を組み合わせる場合は親をすべて記録し、組合せ全体を再評価する。各変更の単独成功を統合後の成功に転用しない。
保存した候補・診断の全履歴を次の担当へ流し込まず、今回の仮説に関係する根拠と反証だけを渡す。

## 実行比較による採用判断

- 要求・権限境界の重要な退行がある候補は採用しない。平均改善で相殺しない。
- 成果が改善した候補、または成果が同等で負担を減らした候補を採用対象にする。同点・不確実な差を無理に勝敗へ変えない。
- 総合成績が劣っても、固有の強みや次の探索価値があれば探索候補として保存する。普段使う採用版と区別する。
- 観測された差と統計的な改善は区別する。確率的な改善を主張するなら同条件の反復とケース別のばらつきを確認する。
- 評価項目を変えたら別版にし、比較する候補を同じ版で再評価する。最終確認の失敗を修正に使ったら、その事例は以後開発用として扱う。

## 反映と報告

採用基準・更新範囲が既に許可されていれば、文言修正ごとに再承認を求めない。新しい要求や重要なトレードオフの判断だけをユーザーへ戻す。
選んだ経路で反映可能な変更を正本へ反映し、導線・validator・必要なコード検証を確認する。commit・push・APM参照更新・installは、その操作が依頼された場合だけ行う。
結果には成果物の場所、反映した変更、実施した確認、未検証・未完了事項を示す。実行比較をした場合は採用候補、比較条件、観測した差と退行も示し、未採用候補と次の仮説をアーカイブから再開できるようにする。
