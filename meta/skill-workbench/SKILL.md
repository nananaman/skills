agent skill のライフサイクルを扱う作業台。
目的は、agent の探索手順を固定することではなく、skill の成果、判断境界、必要な根拠、検証方法を安定させることにある。

## 作業の振り分け

最初に対象の分岐を一つ選ぶ。
複数の分岐が必要なら、完了条件を混ぜずに順番に処理する。

| 分岐 | 使う場面 | 完了条件 |
| --- | --- | --- |
| 改善提案 | 変更案を求められ、編集は依頼されていない | 根拠付きの改訂案、維持する契約、検証方法を会話内で返した。ファイルは変更しない |
| 新規作成／改善 | 新規 skill、または既存 skill の構造、振り分け、ライフサイクルを含む改善 | 変更を作り、適切なレビュー分岐で対応可能な指摘が残っていない |
| 差分レビュー | skill 関連差分の退行確認 | 省略理由、または根拠付きのレビュー結果を返した |
| 全体レビュー | 新規、大幅変更、高頻度、誤作動歴、責務過多の skill の全体確認 | skill 全体と必要な根拠から採用する指摘と採用しない指摘を分けた |
| 一覧の監査 | 一覧にある起動条件の競合、重複、粒度、肥大化、堆積の横断確認 | 問題群、指摘、推奨順、安全確認を報告した |

## 維持する条件

- `SKILL.md` は必要な情報へ到達する軽量な案内にする。詳細は該当する分岐だけが補助文書から読む。
- 固定するのは成果、権限と安全の境界、必要な根拠、検証方法、分岐ごとの完了条件である。探索順序は、誤終了や危険を防ぐ場合だけ固定する。
- description は skill 読み込み前の振り分け用インターフェースとして扱い、本文の要約にしない。
- 指摘は対象本文または実行時の根拠で確認でき、対応可能なものだけを採用する。
- commit、push、APM pin 更新、install は、ユーザーの明示依頼がない限り実行しない。
- 依頼・採用・承認は、指定された対象・操作・範囲・回数に従って引き継ぐ。上位の制約の範囲内でユーザーの明示指示を既定方針より優先し、許可済みの変更を段階ごとに再承認待ちにしない。一回限り・都度承認の指定や、入力・影響の変更による承認範囲の逸脱は別に判断する。
- 情報・権限・必須検証の不足は、それに依存する操作だけを保留する。安全な代替を確認し、独立した作業は続ける。未実施の必須検証を完了扱いにしない。
- skill による確認・停止・未完了を報告するときは、読んだ SKILL.md と該当指示、その適用理由を示す。明示的な条件と自身の解釈を区別する。

## 改善提案

対象、維持する契約、近接 skill を確認し、`references/design-principles.md` に沿って改訂案または差分案と検証方法を会話内に示す。外部資料を主要な根拠にする場合は `references/evidence-synthesis.md` で採否を整理する。
ファイルへの適用、生成物の実行、配布は行わない。静的な提案に実行済みの検証結果を要求しない。

## 新規作成と改善

1. 対象 skill の成果、起動する条件と起動しない条件、権限と安全の境界、根拠、完了条件、プロジェクト固有か汎用かを確認する。
   skill 本文だけのエージェント向けプロンプト契約を最小差分で直す依頼は `improve-agent-prompt` に渡す。
2. 既存 skill の改善では、振り分け、安全と許可の確認、完了条件、出力、失敗時の処理を維持対象として固定する。
3. 新規 skill または責務変更では近接 skill を確認する。横断判断が必要なら一覧の監査を先に行う。
4. `references/design-principles.md` を読み、本文、補助文書、素材、スクリプト、別 skill の境界を決めて変更する。
5. 外部資料を主要な根拠として skill を作成または改善する場合は、草案を作る前に `references/evidence-synthesis.md` を使う。
   観測された症状と資料中の技法候補を対応づけ、主要候補を採用、不採用、要評価のいずれかに分類する。
6. 振り分けが難しい、問題が再発する、または客観評価できる場合だけ `references/eval-loop.md` を使う。
7. 全体レビューへの移行条件は差分レビューの手順3に従う。
   それ以外は差分レビューを実行し、採用した指摘を解消する。
   解消できない指摘は対象と依存する操作を保留し、独立した修正を完了してから、阻害要因、残るリスク、次に必要な最小の行動を報告する。

## 差分レビュー

1. 追跡済みと未追跡を含む skill 関連差分と維持対象を確認する。
2. `references/review-protocol.md` を読み、変更された契約に関係する評価基準と検査だけを選ぶ。
3. 新規 skill、起動条件・責務・権限境界・主要な完了条件を実質的に変える変更、または差分だけでは再発原因を評価できない変更は全体レビューへ移す。
   description の表記修正や利用頻度だけでは移さず、選んだ範囲で何を評価できるか判断する。
   ただし、全体レビューで採用した指摘を修正した後の退行確認は再び移さない。
4. 手順書の形式に従い、省略理由またはレビュー結果を報告する。

## 全体レビュー

1. 対象 skill、直接関係する resources、README 導線を読む。
2. `references/review-protocol.md` を読み、契約の静的検査とリスクに応じた動作確認を行う。
3. 振り分け、責務、情報の配置、権限と安全、完了条件を全体として評価する。
4. 採用した指摘を修正した場合は差分レビューで退行を確認し、手順書の形式で報告する。

## 一覧の監査

`references/audit-protocol.md` を読み、正本を確認してから一覧と必要な問題群だけを調べる。
作業担当の指摘は対象本文で検証し、手順書の形式で報告する。

## 安全上の制約

- 復元しにくい削除、名前変更、統合はユーザーが明示した場合だけ実行する。
- 永続ファイルへ失敗パターン台帳を書く場合は、ユーザーに確認する。確認がない場合は会話内で管理する。

## 報告

結果、変更または提案した契約、検証の証拠、未検証事項を先に伝える。
参照資料の出力例は必要項目の案内として使い、空の節や同じ根拠の再掲は省く。利用者や後続ツールが指定した出力契約は維持する。
