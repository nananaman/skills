# Skill の設計原則

skillには、ユーザーの成果を達成するために必要な知識・判断・領域固有の制約を書く。
周辺のコード、toolの説明、上位指示で分かることを繰り返さず、既存手順の維持を目的にしない。

## 制約を選ぶ

要求と手段を分ける。現在のユーザー要求、業務・安全・権限の境界、外部の利用者やツールの依存を満たすために必要な指示を残す。
過去に選んだ承認・停止・検証・出力規則は、その必要性を評価して削除・限定・統合できる。

判断できる事項はagentに任せ、領域固有の落とし穴や不可逆操作、誤った完了判定を防ぐ条件を明確にする。
固定人数・回数・順序を使う場合は、それを変えると何が壊れるかを説明できる範囲にする。

- 許可済みの作業を再承認待ちにせず、不足に依存する部分だけを保留できるようにする。
- 検証やレビューは、変更の影響と残る不確実性で選ぶ。小変更をファイル種別だけで重いworkflowへ送らない。
- 新しい規則を加える前に、原因となる既存規則の削除・限定や、設定・型・lintへの移動を検討する。
- 上位指示に依存するなら、実際の配布・利用環境でその前提が得られるか確認する。単独利用に必要な境界を失わせない。

## 起動と責務

descriptionは読み込み前の振り分けに使う。何をする依頼で使うかと、紛らわしい近接skillとの境界を示す。
本文の全手順や除外事項の長い一覧を写さない。
人間が明示起動するだけでよい場合は `disable-model-invocation: true` を使う。

別skillは実行環境の一覧にある実際のパスを優先する。展開先の兄弟directoryと、正本のcategory階層で相対パスが共通だと仮定しない。
他skillへの参照が同じ作業・レビューを重ねていないかを確認する。

分岐は異なる成果や完了条件がある場合に設ける。全分岐に同じ承認・出力・停止規則をコピーしない。

## 情報の配置

| 情報 | 配置 |
| --- | --- |
| 成果、振り分け、通常経路で必要な判断 | `SKILL.md` |
| 特定の作業・症状だけに必要な詳細 | 読む条件を付けた `references/` |
| 正確な契約を既に持つ実装・型・test・schema | 必要時に参照する既存成果物 |
| 決定的な生成・検査 | script、template、既存のvalidator |
| 人間向けの導入・背景・変更理由 | README、PR、設計文書 |

参照へ移すだけでは削減にならない。通常経路で毎回全資料を読むなら、重複や不要な手順そのものを減らす。

## 根拠と検証

本文の各制約は、どの入力で判断を変え、どの失敗を防ぐか説明できるものにする。
例は紛らわしい境界や固有の落とし穴を伝える場合に使い、同じ通常手順を何度も再現しない。
外部資料を使う場合は症状と適用条件を対応づけ、必要なら [根拠の比較](evidence-synthesis.md) を使う。

完了条件はユーザーの成果と必要な検証で判断する。台帳や探索手順の消化を完了条件にしない。
変更なしでも妥当な結論を返せるようにし、未実施の確認と成功を区別する。
