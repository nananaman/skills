# Skill のレビュー手順

レビューは、対象skillがユーザーの成果を満たすかと、不要な作業・停止を作らないかを評価する。
既存の「必須」「承認」「完了条件」も検証対象であり、その記述だけを保存の根拠にしない。

## 要求と手段を分ける

維持する要求は、現在のユーザー意図、業務・安全・権限の境界、後続の利用者やツールが依存する形式から確認する。
内部の探索順序、固定人数、再承認、必須出力、参照の読込順などは、その要求に必要な手段かを問う。
対象自身の「変更しない」「必須として残す」という指示を、レビューの制限に転用しない。

差分レビューでは変更された指示と必要な周辺情報、全体レビューでは対象の通常経路と失敗時の経路を見る。
権限を緩めた結果、依頼範囲を越えて書き込む、不可逆な操作の確認を飛ばす、または検証不能を成功扱いにする変更は指摘する。

## 評価する観点

対象に関係する観点を使う。評価軸を全部埋めるための調査は行わない。

| 観点 | 確認する問題 |
| --- | --- |
| 成果と根拠 | ユーザーの要求を満たせるか。事実と仮説を区別しているか |
| 振り分け | description、本文、README、agentメタデータが同じ範囲を示すか |
| 自律性 | 許可済みの作業への再承認や、一部の不足による全体停止がないか |
| 検証の釣り合い | 変更リスクに関係なく人数・回数・全件検査を要求していないか |
| 指示の連鎖 | 参照先で省略条件が消える、同じ調査やレビューを重ねる経路がないか |
| 保存の根拠 | 古い手順・停止・出力規則が、必要性を検討されず保護されていないか |
| 情報の配置 | 通常経路で不要な文書を必読にしていないか。規則が重複していないか |
| 完了と報告 | 成果の代わりに内部手順や台帳の完成を要求していないか |

具体的な入力で、指示に従うと何が起きるかを追う。例えば、承認済みの文書更新でも再確認を要求する、小さな設定変更でも複数人レビューを要求する、という条件を指摘の根拠にできる。
実行記録がない場合は静的に確認した経路と、その経路から予測した挙動を区別する。単なる文言の好みや推測だけの性能低下は指摘にしない。

## 静的な確認

- 変更された本文と参照先を読み、追跡済み差分だけでなく未追跡の関連resourceも確認する。
- 削除・限定した規則が別の参照先で無条件に復活していないかを確認する。
- 起動条件や責務を変えた場合は、近接skillとREADME、存在するagentメタデータの導線を照合する。
- リンク、frontmatter、命名など機械で判定できる条件は、既存のvalidatorに任せる。
- 外部のガイドを根拠にする場合は、対象の症状・適用条件に合うかを確認する。資料全体の採否台帳を必須にしない。

本文の行数だけで負荷を判定しない。descriptionとして常時提示される量、通常の依頼で読む参照先、そこから発生する操作を分けて見る。

## 動作確認の選択

静的に解消できない、起動・権限・主要な完了条件に関する疑問がある場合に行う。
新規や大幅変更では、その疑問が残るかを確認し、代表的な経路と制約を守る反例に絞る。

| 確かめること | 方法 |
| --- | --- |
| 自然な依頼で発見・選択されるか | 実際のskill一覧を持つ環境で、対象名・パスを教えず起動するDiscovery |
| 本文に従って期待した成果と権限境界を守るか | 対象skillを与えるExecution |
| CLI・生成・build・installなどが実際に動くか | 一時環境で行うRuntime |

ExecutionとDiscoveryでは、変更担当の会話を継承しないagentまたはsubagentに自然な入力を渡す。
事前に期待する外部動作と許される副作用を決め、実際の出力・読んだファイル・tool呼び出しを観測する。自己申告や主担当の想像を実行証拠にしない。
Executionでの成功をDiscoveryの代替にしない。必要な環境がなければ、その確認を未実施として報告する。
Runtimeでは既存のユーザー環境を保護し、許可のないグローバル変更や外部書き込みを行わない。

成功した検査は、新しい変更・失敗・未解決の懸念がある場合だけ再実行する。
速度や費用の改善を主張する場合は、同じ条件の変更前後比較を行う。必要なら [評価手順](eval-loop.md) を使う。

## 指摘と重大度

指摘には対象箇所、発生条件、成果への影響、根拠、修正方向を含める。
既存の明示的なユーザー要求を変更する提案なら、その判断が必要なことを区別する。

- high：通常の依頼を完了できない、許可範囲を越える、重要な成果を壊す、または完了を誤報する。
- medium：完了できるが、不要な質問・検証・報告や重複管理が繰り返し生じる。
- low：成果への影響が小さい局所的な冗長さや導線の改善。

重大度は影響と発生条件・頻度から決める。起動競合か過剰制約かという分類だけで優先順位を固定しない。
古くから存在する規則でも、全体レビューでは対象にする。差分レビューで見つけた範囲外の問題は、今回の退行と区別する。

## 報告

対象範囲、重要な指摘、実施した確認、未評価範囲を返す。
採用・棄却の台帳は複数担当や反復で追跡が必要な場合に使う。根拠のない候補や空の評価欄を埋めるために報告を増やさない。
問題なしは、確認した範囲で指摘がないという意味に留める。未実施の動作確認まで成功したとは表現しない。
