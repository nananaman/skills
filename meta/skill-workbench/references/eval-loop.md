# Skill の効果を比較する

起動・実行の選択が静的に判断できない、問題が再発する、または品質・費用の改善を実証したい場合に使う。
すべてのskill変更で比較実験を必須にしない。

## 比較を準備する

改善したい挙動と、維持すべきユーザーの成果・権限境界を選ぶ。
合格条件は出力や副作用など外部から観測できるものにし、既存の内部手順を実行すること自体を正解にしない。

自然な依頼、起動しない紛らわしい入力、制約を残すべき反例から、変更のリスクに合う例を選ぶ。
変更前のskillと変更後、または新規ならskillなしとありを比較する。識別できる版を保持する。
入力、合格条件、モデル、推論設定、tool、実行環境を比較前に固定する。

## 実行と判定

- 起動を検証するDiscoveryは、実際のskill一覧を持つ環境で対象名・パスを教えずに行う。選択済みの本文を実行するExecutionと区別する。
- 変更担当の会話を継承しないagentまたはsubagentを使い、自己評価だけで成功にしない。
- 出力、読んだファイル、tool呼び出し、副作用と、取得できるなら所要時間・tokenを記録する。
- 品質と権限境界の合否を先に判定する。合格条件を維持した場合だけ、不要な質問・検証・報告や費用の削減を改善と数える。
- 新旧が両方合格する条件も、退行防止の基準として保持する。品質差がなければ差がないと報告する。
- 技法探索の評価では候補名だけでなく、症状への適合と根拠、重要な代替案の見落としを確認する。
- 確率的な改善を主張する場合は同条件で複数回実行し、単発結果を一般化しない。

環境を用意できない場合は、静的に確認したことと未実施の評価を分ける。作者の読み合わせを実行型評価の代替にしない。

## 修正と終了

評価で確認した失敗の原因を直す。規則の削除・限定・統合も候補にし、評価用入力だけへの過剰適合を避ける。
比較中はモデルや実行環境など別の変数を同時に変更せず、複数ファイルにまたがる同じ原因は一貫して直す。
新しい変更・失敗・未解決の懸念がある範囲だけ再評価し、必要な条件を満たしたら終える。

結果には比較した版、入力と実行条件、観測した成果・副作用、品質と費用の差、未検証事項を示す。
詳細な台帳は再現や複数回の比較に必要な場合に作り、短い確認へ全項目を要求しない。
