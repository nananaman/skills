# 評価と更新の手順

## 評価信号を作る

評価ケースと採点基準の一式を suite と呼ぶ。この手順は実行比較を行う場合に使う。比較できない場合の反映と完了は [本文](../SKILL.md)の「評価できない場合」に従う。

ユーザーの成果と副作用を判定する。旧 skill の手順遵守や、ファイルが存在することだけを合格条件にしない。
明示されたユーザーの好み・規則は要求として扱う。観測から推測した成功要因とは区別する。

- train：更新担当が診断・編集に使える事例。成功例、失敗例、必要な制約を守る反例を含める。
- validation：候補選択に使う事例。詳細を更新担当へ渡さず、比較担当が採否を判断する。
- test：選択済み候補の最終確認用。候補選択や修正に使った事例は独立した最終評価ではない。

同じ元タスクの言い換えや近似例は同じ群へ置く。少数事例で分離できなければ探索的な評価と報告する。
検証結果の詳細を原因分析に使う必要があれば、そのケースを新しい suite で train へ移し、新しい確認ケースを用意する。

決定的に判定できる条件は script で検査する。主観的な品質は具体的な基準を先に定めた匿名比較や人の評価を使う。
既知の良い出力・悪い出力で評価器を確認し、両方通る条件や成果を見落とす条件を直す。常に成功する重要な退行チェックを、差が付かないという理由だけで削除しない。
ユーザーの空欄コメントは「未評価」と扱う。満足・採用の意思を推測しない。

## 比較条件と実行

自然な依頼での Discovery、選択済み本文の Execution、CLI 等の Runtime を区別する。
Discovery は対象名・パスを依頼へ付加せず、近接 skill も含む実際の catalogue で評価する。
Execution の成功で起動精度を証明しない。複数 skill が連鎖する主要ケースも含める。

同じ suite、初期ファイル（fixture）、モデル、推論設定、tool、上位指示、反復番号で親と子を比較する。
実行担当には課題と利用可能な情報だけを渡す。診断履歴、採点結果、正解例を渡さない。
新しい会話は文脈の分離であり、filesystem や権限の隔離ではない。必要な分離は実行環境側で用意する。

成果物、tool 呼出し、実行記録、経過時間、取得できた token を保存する。採点担当は成果物を直接確認する。
エラー、timeout、未採点、判定不能と評価不合格を分ける。欠測をゼロへ埋めず、文字数を token へ代入しない。
比較の対応が欠けた試行は改善の証拠にしない。都合の悪い試行を除外する場合も、理由と元の結果を残す。

## テキストによる更新方向

更新担当は train の実行を「改善」「悪化」「継続失敗」「安定成功」に分け、仮説を作る。
一度の失敗から指示不足を決めつけない。知識不足、起動競合、過剰手順、ツール障害、環境差、評価器の誤りを切り分ける。

更新方向には、対象パスと層、追加・削除・置換・移動、変える判断、その根拠と反証を含める。
例：「小変更でも二重レビューを起動した。本文の全件レビュー指定を限定する。不可逆操作の確認ケースは維持する」。
最終出力だけから原因を断定せず、実行中の分岐と照合する。必要なら該当変更を外す比較で仮説を確かめる。

momentum は、関係する診断を反復をまたいで照合するための記憶である。support と counterevidence の実行参照を持つ。
同じ原因の再発、異なるケースでの成功、反証をもとに適用範囲を更新する。回数だけで正しさを決めず、否定された仮説も再提案を避けるため保存する。
この記憶は更新担当用であり、通常利用の skill へ毎回読み込ませない。

編集予算は一度に検証する診断数と触る層・責務で決める。例えば初期は複数の関連診断、収束時は一つの診断に絞る。
固定の文字数や研究のスケジュールを無条件に移植しない。差分を予算と照合し、無関係な変更を分離する。

## 採否と再開

補助 CLI の比較結果は観測上の判定であり、自動採用や統計的有意差の判定ではない。
必須条件の退行は採用を止める。成果同等で費用を減らした場合は簡素化として採用できるが、両方失敗を品質同等の根拠にしない。
最終確認でも必要な成果を満たすことを確認する。未見事例での合格を、未評価のモデルや領域へ一般化しない。

候補 ID、親、比較レポート、採否、判断根拠、残る不確実性を decision として保存する。
採用版の選定とは別に、特定ケースに強い候補や構造の違う候補を探索の親として残す。
予算を使い切った、意味のある改善が止まった、必要な成果を満たした、のどれで終了したかを示す。
