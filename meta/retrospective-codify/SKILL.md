# 経験を次の改善に使える形へ残す

振り返りの成果は、次の判断を改善する証拠と仮説である。一回の失敗と、その場の解釈を一般規則へ直結させない。

## 事例を取り出す

会話と実行記録から、元の依頼、その時点の許可・制約、実際の判断と結果、期待した成果を対応づける。
失敗例だけでなく、成功例、途中の修正、最初の想定を覆した根拠も見る。見ていない失敗や反例を創作しない。
再利用できる判断がない場合は、規則の追加なしで終えてよい。

各事例は、入力と初期状態、観測した挙動、期待する成果、証拠への参照、原因仮説、適用範囲、反証または未確認事項を持つ。
再実行できる状態がなければ、観測事例として残し、実行可能な評価ケースと区別する。
実務ログに公開できない内容がある場合は、公開 repository 外の実験領域へ保存する。再現用の初期ファイル（fixture）は必要な関係を保って匿名化する。

## 要求・事実・仮説を分ける

| 内容 | 扱い |
| --- | --- |
| ユーザーが明示した要求・好み | 採用された内容を要求として適切な正本へ反映する |
| 設定・型・lint で決定的に保証できる事実 | 対象 repo の既存機構を修正し、通常のコード検証を行う |
| 指示や手順を変えれば挙動が良くなるという仮説 | 事例と証拠を `skill-workbench` の評価ループへ渡す |
| 一回限り、既存で十分、根拠不足 | 変更なし、または未確定の仮説として報告する |

既存の指示・設定・近接 skill を検索し、失敗を生んだ規則や重複も調べる。追記を既定にせず、削除・限定・統合・廃止・コードへの移行も仮説にする。
過去の類似診断があれば根拠と反証を照合する。単に何度も言及されたという理由で一般化しない。

## 評価ループへ渡す

利用可能な一覧から `skill-workbench` の実際のパスを読む。
元の事例を診断・編集に使う開発用ケース（train）の候補として渡し、成功条件、反例、診断、期待する更新方向を整理する。
診断の確からしさと改善の実証を分ける。別文脈で実行し、別のケースで検証するまでは未検証の更新候補である。
診断を反復をまたいで照合する記憶を momentum と呼ぶ。生の事例を記録しただけでは実証済みの根拠にせず、評価済みの実行参照ができたら workbench の診断アーカイブに保存する。

ユーザーが具体的な対象・内容を既に採用している、または範囲と基準を定めて改善を任せている場合は、その許可で進める。
それ以外の永続的な規則変更は、対象・具体案・根拠・確認方法を示し、採用された内容だけ反映する。
採用判断がまだでも、事例整理と安全な調査は進める。commit・push・APM更新・install は各操作が依頼された場合だけ行う。

## 結果

得られた事例、証拠付きの仮説、反映した要求や修正、評価待ちの候補を短く報告する。
実験領域がある場合は再開に必要な参照を示す。規則数や振り返り文書の完成を改善成果にしない。
