# 振り返りの知見を規則へ固定する

次回の判断を改善する知見を、最も適した場所へ固定する。原因となった規則の削除や適用範囲の縮小も成果とする。

## 知見と原因

今回の試行、結果、判断を変えた根拠から「最初に分かれば遠回りを避けられたこと」を整理する。
失敗があれば最初の試行と最終解を対応づける。記録がなければ失敗を創作せず、不確かな原因は仮説として扱う。

再利用できる判断がない、既存の仕組みで十分、または一回限りの対応なら、新しい規則を作らず終えてよい。
プロジェクト固有でも、同じrepoで再利用できる知見は対象にできる。

## 既存の仕組みを調べる

症状、ツール名、判断語から、対象repoの指示・設定・lint・関連skillと必要な参照資料を検索する。
グローバル規則を扱う場合はmanifestと正本を確認し、展開物を直接編集しない。
重複だけでなく、既存の規則が失敗や不要な確認を発生させていないかを調べる。

| 判断 | 対応 |
| --- | --- |
| 既存の規則が不要な作業・停止を生む | 削除、適用範囲の限定、より適した層への移動 |
| 同じ目的の規則が重複・競合する | 既存規則を統合・修正し、古い記述を撤去 |
| 設定・型・lint・formatterで保証できる | 対象環境の仕組みで固定 |
| 必要な知見が既存の仕組みにない | 適用範囲を絞って追加 |
| 既存で十分、再利用不能、根拠不足 | 追加なし、または未確定の判断を報告 |

追記を既定にしない。削除・限定する場合も、ユーザー要求や領域固有の安全条件を損なわないか確認する。

## 配置先

- 決定的に検査・設定できる規則は、そのrepoの既存の設定や検査機構へ置く。新たなlint基盤の導入は、その費用が必要な場合に限って提案する。
  - コーディング規範を追加・修正する場合は、既存formatter・型・linterや単純な文字列検査で保証できる部分を先に選ぶ。既存機構では不十分で、コードの形や配置で判定できる部分は `ast-grep-practice` へ渡す。意図、対象範囲、禁止例・許可例、例外、提案か導入かの依頼範囲を引き継ぎ、確認済みの判断を繰り返さない。
  - ガイドには意図・適用範囲・例外と検査への参照を残す。意味・設計判断が必要な部分はガイドとレビューで扱い、一部の構文検出を規範全体の保証としない。今回の知見に関係する規則だけを扱い、全件棚卸しや新しいrule作成を必須にしない。
- プロジェクト限定の知見は、そのrepoの設定、AGENTS.md、project skillへ置く。
- 複数repoで共通して毎回必要な短い指示だけを、グローバルAGENTS.mdの正本へ置く。
- 作業固有の知識・判断は、汎用skillの正本である `nananaman/skills` またはproject skillへ置く。近接skillが同じ責務を持つなら統合・更新を検討する。
- 過去の経緯だけなら、commit・PR説明や作業記録で十分かを判断する。

例えば、一つのrepoでpackage managerのversion差が問題になった場合は、そのrepoのversion指定とCIを確認する。一度の成功から、全repo共通の「常にversion X以上」という規則へ一般化しない。

## 提案と適用

知見ごとに、変更する対象と具体的な削除・限定・更新・追加の案、その理由、確認方法を示す。複数の採用候補には番号を付ける。
変更なしの場合は既存の根拠を短く示す。学び・重複・不採用を同じ情報で何度も列挙しない。

将来の挙動を変える永続的な規則は、ユーザーが採用した内容だけを反映する。会話で対象と内容が具体的に採用・実装指示されていれば再承認は求めない。
未採用の候補は提案に留める。commit、push、APM pin更新、installは、別途その操作を依頼された場合だけ行う。

変更を適用したら、撤去対象の参照が残っていないかと、残すべき要求が満たされるかを確認する。
skillを変更した場合は `skill-workbench` でレビューする。設定やlintの変更は対象環境の検証を行い、実行コードを変更する場合は `implement` の該当手順に従う。

結果は、採用した変更と配置先、検証結果、未適用の提案や未確認事項があればその内容を返す。規則を増やすこと自体を完了条件にしない。
