# 変更履歴を書く

利用者・運用者・開発者が、何が変わり、どんな対応が必要か分かる変更履歴を書く。

## 対象を確認する

依頼された差分範囲と出力先を確認し、既存のCHANGES.mdがあれば形式・粒度・言語を読む。
差分を取得できる場合は実際の変更を読み、commit messageの言い換えだけで済ませない。
対象にはstaged / working tree / branch / commit range / PRの差分を使う。複数の解釈で内容が変わり、依頼や作業文脈から判断できない場合だけ確認する。

CHANGES.mdがない場合、明示の新規作成依頼なら最小構成で作成し、提案だけなら会話内に案を返す。作成・更新を依頼済みなら、形式案の再承認を着手条件にしない。
既存のUnreleasedがあればそこへ追記し、なければ既存形式に合わせて追加する。公開済みの版の履歴を無断で書き換えない。

## 内容と形式

- 変更された機能・設定・APIを主語にし、作業の実況ではなく観測できる変化を書く。
- 一項目は一つの変更を基本にし、単なる「修正」「追加」で影響が伝わらない場合は結果を補う。
- 互換性の破れや移行が必要な場合は、変更内容と利用者が取るべき対応を明確にする。
- 意図・影響・version・日付など、差分や依頼で確認できないことを捏造しない。不明な点は分離し、書ける変更まで止めない。
- issue / PR番号、分類、言語は既存形式に合わせる。新規作成で言語指定がなければ日本語にする。
- 既存の同じentryを重複追加せず、該当しない空見出しを作らない。

新規作成や既存分類がない場合は、`# Changes`、`## Unreleased`の下に必要な分類だけ置く。
分類の候補はAdded、Changed、Deprecated、Removed、Fixed、Security。Internalはその読者に意味がある場合だけ使い、移行説明が長ければMigration Notesを設ける。

release noteでは利用者への影響を優先し、内部変更は重要なものに絞る。PR用entryは変更履歴の粒度に留め、内部レビュー手順やテスト結果を混ぜない。
文案作成の依頼をrelease公開の許可とは解釈しない。

対象差分、作成・更新または提案した出力先、判断に必要な未確認事項を簡潔に報告する。
