# 解説の情報設計

解説は、用語や機能を列挙する文書ではない。
読者が対象の全体像を持ち、具体的な挙動を追い、境界や失敗を理解して、次の操作や判断へ進めるように設計する。

## 読者の到達点を定める

最初に、次を一文で決める。

- 誰が読むか。既知の前提、専門用語、利用経験は何か。
- 読者が説明後に理解、確認、実行、判断することは何か。
- 読者が困っている場面は何か。検索で一部だけ読むのか、最初から通読するのか。
- どこまで説明するか。対象外の機能、詳細実装、運用手順を区別する。

製品の利用者やシステムの利用者を、そのまま解説の読者とみなさない。
同じ機能でも、初めて概念を知る人、導入を判断する人、障害を調査する人では必要な順序と粒度が異なる。

## 説明するモデルを作る

本文を書く前に、対象を次の要素へ分解する。

- 登場人物、コンポーネント、責任の境界。
- 入力、出力、保存されるもの、変換されるもの。
- 状態、状態を変えるイベント、状態を確認する方法。
- 同期・非同期、時間、順序、再実行、失敗、重複の扱い。
- 読者が操作する境界と、内部で起きる処理の境界。

このモデルのうち、読者の到達点に必要なものだけを本文へ出す。
内部の詳細を隠す場合は、隠したことが誤解や運用上の危険につながらないか確認する。

## 情報の順序を選ぶ

一般的な解説では、次の流れを出発点にする。

1. **要点**：この対象は何を解決し、読者は何を理解できるようになるか。
2. **全体像**：登場人物、入出力、主要な境界を短く示す。
3. **一つの具体的な流れ**：入力から結果までを、状態やデータの変化に沿って追う。
4. **設計上の理由**：なぜその流れや境界になっているか。必要な場合だけ説明する。
5. **失敗、重複、境界条件**：期待どおりでない場合に何が起きるか。資料で確認できる範囲に限る。
6. **次の行動**：試す手順、確認先、関連資料、判断事項。

用語辞書から始めると全体の役割が見えにくい。
用語は、具体的な流れを読むために必要になった場所で定義し、似た用語との差分を同時に示す。

## 例と図を本文へ結びつける

- 例は、全体像のどの要素を具体化しているかを示す。
- 比喩を使う場合は、対応する部分と対応しない部分を明らかにする。比喩を仕様の根拠にしない。
- 図の矢印、カード、色、アイコンが何を表すかを凡例または本文で説明する。
- 図を見なくても、本文だけで主要な登場人物、順序、状態、制約が分かるようにする。
- 実際の仕様と架空の例を混ぜない。サンプル値、仮の名前、簡略化した流れはその旨を示す。

装飾的なカードや段階表示を増やしても、読者のメンタルモデルは整わない。
各視覚要素が、読者のどの疑問を解消するかを説明できる場合だけ使う。

## 非同期処理と状態遷移を説明する

非同期の対象では、要求を受けたこと、処理が進んでいること、状態を確認すること、結果を利用することを区別する。
各段階を誰が担当し、何を渡し、どの状態を見ればよいかを明示する。

資料に根拠がない限り、再試行回数、ポーリング間隔、通知方式、成功条件、冪等性を推測で補わない。
分からない場合は未確認事項として書き、確定した挙動と混ぜない。

## HTMLとして届ける場合

- まずテキストの要点と見出し階層を固め、CSSやアニメーションを後から加える。
- `title`、`lang`、一つの `h1`、論理的な `h2` と `h3` を整える。見出しを見た読者がページの骨格を理解できるようにする。
- 色、アイコン、位置だけで状態や意味を伝えない。必要なテキスト、ラベル、代替テキストを用意する。
- 横幅を変えても、流れ、表、コード、図、リンク先が読めるようにする。
- インタラクションで情報を隠す場合、初見の読者が重要な制約へ到達できる導線を置く。主要な意味を CSS や JavaScript だけに依存させない。
- 既存のコンポーネントや `salmon-flake` の規約がある場合はそれに従うが、コンポーネントの都合で説明の順序や内容を変えない。

## 解説のレビュー

- 初見の読者が、ページの要点と自分に必要な箇所を短時間で見つけられるか。
- 全体像を読んだ後、具体的な一つの流れを最後まで追えるか。
- 似た用語、状態、責任範囲を取り違えないか。
- 期待どおりの例だけでなく、失敗、重複、未確認の境界が分かるか。
- 図、コード、本文、実装の現状が一致しているか。古い例を仕様として扱っていないか。
- 読み終えた読者が、次に確認または実行することを判断できるか。
