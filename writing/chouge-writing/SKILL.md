# 文書の設計、執筆、レビュー

読者が必要な情報を理解し、文書の目的に応じた判断や行動へ進める文書を作る。
文章を整える前に、誰に何を伝え、何を判断・実行してもらう文書なのかを定める。

## 使いどころと境界

- 文書、記事、実験・検証報告、解説、設計・判断資料、状況報告、手順書、HTML reportの新規作成、推敲、構成レビューに使う。
- 一言の返答、コード内の短いコメント、機械的な形式変換など、文書の設計や論証が成果を左右しない作業には使わない。
- PRD、Design Doc、論文、サイト、PDF、スライドなどに固有の必須項目や出力形式がある場合、それらを優先する。この skill は、固有 skill や template が定める内容を置き換えず、読者、目的、構成、根拠、レビューを補う。
- HTML、PDF、DOCXなどのレンダリングや配布に専用 skill・toolがある場合はそれを使い、この skill では内容と情報設計を扱う。

## 文書の契約を決める

執筆前に、次の情報を文書の契約として整理する。

- **読者**：誰が読むか、何を知っていて何を知らないか、どの状況で読むか。
- **目的**：読者に何を理解、判断、選択、実行してもらうか。読む前の疑問や迷いが、読んだ後にどう変わってほしいか。
- **媒体**：Markdown、HTML、短い報告、長文記事など、どのように読まれるか。
- **範囲**：扱うこと、扱わないこと、前提、期限、必要な粒度。
- **根拠**：参照できるコード、データ、実験、既存文書、観測事実と、まだ確認できていないこと。
- **成果物の状態**：草稿、レビュー依頼、採用判断用、公開版など、読者がどの程度の確定性を期待するか。
- **参照資料の役割**：構成・粒度の参考なのか、事実の根拠なのか、転記対象なのか。

「この文書は、[読者]が[目的の判断・行動]をできるように、[対象]を説明・報告する」と一文で言える状態を目指す。
依頼、既存文書、リポジトリ、出力媒体から判断できることは自分で補う。
読者や目的の不確実性が構成や結論を変える場合だけ、必要な判断を質問する。
それ以外は妥当な仮定を置き、文書内または報告時にその仮定を明らかにする。

製品やシステムの対象ユーザーと、文書を読む人は別である。
PRDの対象ユーザーを、PRDの読者と取り違えない。

参照資料は、構成や表現の参考として与えられたのか、今回の文書でも成立する事実として与えられたのかを分ける。
参照資料の状態、未解決事項、TODO、固有の判断を、今回の文書へ理由なく引き継がない。
参考文書の章立ては構成と粒度の出発点であり、章数や文字量の目標ではない。

## 伝える内容に優先順位をつける

読者と目的から、最も持ち帰ってほしいことを一文で定める。
長い文書では、それを支える少数の要点と、今回は伝えない話題も決める。
リファレンスのように参照して使う文書では、読者が探す情報や実行する作業を軸にする。
この整理は執筆の判断に使い、毎回一覧を提示したり承認を求めたりしない。

説明を足す、残す、削るときは、次の順で判断する。

1. この読者が理解、判断、実行するために必要か。
2. 本文のこの位置に置くことで、最も伝えたいことが明確になるか。
3. 詳しく説明する、短く触れる、参照先へ分ける、省く、のどれが適切か。

目的に関係する情報でも、すべてを本文で詳しく扱う必要はない。
重要な要点には説明を割き、補助的な内容は短くする。
納得や再現に必要な具体例、コマンド、手順、非自明な因果、順序を示すつなぎは残す。
説明が自明かどうかは、書き手ではなく想定読者の知識で判断する。
短さや狙った読後感のために、事実、不確実性、成立条件、指定された必須情報を省かない。

## 文書の型と構成を選ぶ

目的と情報の優先順位に合う型を選び、複数の節が必要なら本文を書く前に見出しの案を作る。
短い単一論点の文章では、指定形式で必要な場合を除き、見出しを置かず段落でつないでよい。
次の型は出発点であり、目的に寄与しない節は削る。

reference は一度にすべて読まない。まずこの `SKILL.md` で文書の契約と型を決め、次の routing に従って必要なものだけを読む。

- 通常の新規作成・大幅な改稿：型別 reference がなければ[生成時の文章原則](references/writing-principles.md)を読む。
- 実験・検証報告：[実験・検証報告の設計](references/doctypes/experiment-report.md)を優先し、一般原則は重ねて読まない。
- 解説・ガイド・解説HTML：[解説の情報設計](references/doctypes/explanation-design.md)を優先し、一般原則は重ねて読まない。
- 文単位の日本語推敲や、不自然な表現の診断：[日本語の読みやすさ](references/japanese-readability.md)だけを追加で読む。
- 長文記事・書籍：[長文の構成と語り](references/long-form-writing.md)だけを追加で読む。
- 長文、重要な判断資料、明示的なレビュー依頼：[レビュー手順](references/review-guide.md)を追加で読む。

一つの依頼で複数の型にまたがらない限り、一般原則と型別 reference を併読しない。短い文書や単純な修正では、reference を読まず本文の規則だけで進めてよい。

| 文書の型 | 基本構成 |
| --- | --- |
| 判断・提案 | 要約・求める判断 → 背景と問題 → 選択肢と評価基準 → 推奨案と理由 → 影響とリスク → 次の行動 |
| 実験・検証報告 | 要約 → 背景と問題 → 問い・仮説 → 手法と採用理由 → 条件・データ → 結果 → 考察と限界 → 結論・次の判断 |
| 解説・ガイド | 読者の到達点 → 背景・前提 → 概念モデル → 具体例・手順 → 失敗例・境界条件 → 次の参照先 |
| 状況・実績報告 | 対象期間・範囲 → 結果と基準 → 差異や要因 → リスク・依頼事項 → 次の行動 |
| リファレンス・手順書 | 対象範囲 → 前提・準備 → 手順 → 期待結果 → 失敗時の対応 → 検証・復旧 |

判断や行動を求める文書は、読者が先に結論と依頼事項を見つけられるようにする。
本文には、読者に直ちに求める判断・行動と、保留中に行う暫定対応を分けて書く。
担当者や期限が資料にない場合は、人物名や日時を創作せず、意思決定者がそれらを決めること自体を次の判断として示す。
読者が概念を理解する必要のある解説や、導出自体が価値になる長文では、前提から段階的に進めてもよい。
長文記事や書籍で場面・導出を設計する場合だけ、routing に従って[長文の構成と語り](references/long-form-writing.md)を追加で参照する。

## 根拠と論証を整理する

- 観測した事実、そこからの解釈、仮定、推奨、未確認事項を区別する。
- 重要な主張には、根拠、適用範囲、根拠からそこまで言える理由を対応づける。
- 因果を主張するときは、仕組みまたは実験設計上の根拠を示す。相関、同時に起きたこと、手法の有用性を同一視しない。
- 実験・検証では、何を確かめたいのか、なぜその手法を選んだのか、測定指標・比較対象・条件は何か、結果から何が言えて何が言えないのかを分けて書く。
- 「有用だった」のような評価は、評価基準、比較対象、観測結果に結びつける。結果が仮説を支持しない場合も、その範囲と次の判断を記録する。
- 例や一部の結果が支える範囲を越えて一般化しない。確認していないことを、滑らかな文章で確認済みのように見せない。
- 推測、仮定、可能性、ログからの推定、反実仮想の不確実性を、文章を強くするために事実として書き換えない。
- 用語、分類、前提を文書全体で揃える。異なる原因や判断を一つの上位語で隠さず、同じものとして扱う根拠がある場合だけまとめる。

## 構成に沿って執筆する

- 見出しだけを読んでも、問題、根拠、判断、次の行動の流れが追えるようにする。
- 読者が短時間で判断する文書では要約や結論を先に置く。解説では、理解に必要な前提を先に置く。
- 一つの段落では一つの論点を進め、冒頭で何を扱うか分かるようにする。接続表現は論理関係を示す場合だけ使う。
- 一つの節に一つの役割を持たせる。隣接する言い換えや根拠の丸ごとの再説明は削る。離れた箇所で読者が判断や前提を思い出すための短い再提示は、その位置で必要になる場合に使う。直前の説明だけで次へ進めるなら、結末という理由だけで要約を付けない。
- 例、表、図、コード、スクリーンショットは、読者の理解や判断を変えるものだけを置く。検証や再現に必要な具体は残し、装飾的な詳細は省く。
- 見出しは対象、問題、方法、判断を具体的に予告する。質問型や結論型も、本文を正確に表し、全体の流れを追う助けになるなら使う。「導入の工夫」より「既存データを移行せずに試す」のように中身が分かる名前にする。指定された「結果」「考察」などの節名は守る。

## 書き上げた後にレビューする

執筆後は、文章を整える前に内容と構造を読み直す。
レビューで見つけた問題は修正し、修正後の文書をもう一度読む。
長文、重要な判断資料、明示的なレビュー依頼では、routing に従って[レビュー手順](references/review-guide.md)を追加で読み、確認の深さと記録方法を選ぶ。

### 読者と目的

- 想定読者が、なぜ読むのか、何が分かればよいのかを冒頭で理解できるか。
- 文書の結論、求める判断・行動、次に読む・行うことが見つかるか。
- 読み終えた人が最も強く受け取ることは、狙った理解、判断、行動や読後の変化と合っているか。
- 各節が読者の目的に貢献し、補足の量や配置で最も伝えたいことを埋もれさせていないか。

### 構造と論証

- 見出しの並びだけで、問いから結論までの流れを追えるか。
- 先に必要な定義や前提を置いているか。前方参照した論点を実際に回収しているか。
- 事実、解釈、提案、未確認事項、未決定事項、範囲外を読み分けられるか。
- 重要な主張の根拠、適用範囲、限界が不足していないか。
- 再提示はその位置で理解や判断を助けるか。役割のない言い換えや再説明を削ったか。
- 見出しと説明量に情報の優先順位が表れているか。削った結果、納得や再現に必要な具体、条件、つなぎが失われていないか。
- 文書の状態に対して内容が適切か。読者へ渡す成果物に、テンプレートの記入指示、内部作業メモ、`TODO`、`FIXME`、`TBD`、未置換のプレースホルダーを残していないか。未確定事項を残す場合は、読者向けの判断事項として書いているか。
- 未決定事項を残す場合、本文の採用方針と矛盾させず、読者が次に決めることとして一箇所に整理しているか。
- 参照資料から移した事実、今回の提案、作業中のメモが区別されているか。参照資料の固有名詞や判断が対象に適用できるかを確認したか。

### 表現と媒体

- 主語と動詞が具体的で、抽象語、空虚な形容、姿勢だけの宣言、LLMらしい定型句に頼っていないか。
- 用語、数値、参照先、リンク、図表、コード例が文書内で一貫しているか。
- Markdown、HTMLなどの媒体で、見出し、表、コード、リンク、画像が読者の理解を妨げていないか。
- HTML、PDF、DOCXなどの成果物は、可能なら実際の viewer / renderer で開き、崩れや読めない状態がないことを確認する。

短い日常文書に重いレビュー手順を課さないが、内容の正しさや判断への影響が大きい文書ほど、根拠と限界を重点的に確認する。
独立したレビュー担当を使える場合でも、担当者の存在だけで内容を確認済みとはせず、指摘を根拠付きで採否する。
チェック項目を消化したことではなく、読者が目的を達成できる状態を完了条件にする。

### 解説HTMLを作る場合

- CSSを書く前に、ページの一文の要点、想定読者の到達点、読者が読み終えた後に確認・判断することを決める。
- 情報の順序は、必要に応じて「全体像 → 一つの具体的な流れ → 失敗・重複・境界条件 → 読者の次の行動」とする。視覚的な区切りを増やすことを、内容の設計の代わりにしない。
- 非同期処理や状態遷移を説明する場合、要求を受ける、処理を進める、状態を確認する、結果を利用するという各段階と、段階をまたぐ仕組みを本文で説明する。資料にない再試行、間隔、通知方式、成功条件は補わない。
- 図やカードは、登場人物、保存先、状態、矢印の意味が本文と一致するようにする。図が読めなくても主要な関係を本文だけで追えるようにし、装飾的な図を増やさない。
- `title`、`lang`、`h1`から始まる見出し階層、十分な本文、リンクやコードの意味を整える。色やアイコンだけに意味を持たせず、必要な代替テキストやラベルを付ける。
- 画面幅を変えたときに、横並びの流れ、表、図、コードが読めるかを確認する。可能ならブラウザーやHTML viewerで開き、開けない場合は実施できなかった検証として報告する。

## 日本語で書く場合の規範

文単位の推敲で迷った場合は、[日本語の読みやすさ](references/japanese-readability.md)を参照する。

- 定着した用語・訳語を使い、具体的な主語と動詞で書く。「重要な」「多角的な」「包括的な」「掘り下げる」のように、内容を増やさない強調や動詞を置かない。
- 同じ主張の言い換え、直後の要約、読者との架空の問答、修辞疑問、決め台詞を多用しない。主張、限定、理由をそのまま書く。
- 不確実性を示す「かもしれない」「だろう」などは、根拠なく弱めるためだけに使わない。推測や可能性を表す場合は残す。
- Markdown原稿は一文一行、段落間は空行にする。成果物の形式に別指定がある場合はそれに合わせる。
- コード、差分、ログ、設定の断片はコードブロックへ置く。本筋から外れる補足は、形式が対応する場合に脚注へ分ける。
- 用語の初出の定義は太字にし、以後の言及や引用・通称は「」を使う。用語と定義の列挙は「**用語**：説明」とする。強調のためだけに太字を増やさない。
- 日本語の地の文・見出しでは、ダッシュ類による挿入や区切りを使わず、括弧、句点、読点、助詞でつなぐ。範囲のenダッシュ、定着した英語の名称、コード、書誌情報は除く。
- 日本語の並列に中黒を使わない。ただし単一の固有名詞内は除く。

## 完了条件

次を満たしたら文書を完成扱いにする。

- 読者、目的、媒体、範囲、前提が明確である。未確定なら仮定と未解決事項が分かる。
- 目的に合う構造が選ばれ、各節の役割が重複していない。
- 結論、回答、判断、または次の行動が、文書の目的に応じて明確である。
- 主張が根拠の支える範囲に収まり、事実と解釈と不確実性が保たれている。
- 読者向け成果物に内部作業メモ、TODO、コメント、プレースホルダーが残っていない。未決定事項を残す場合は、本文と矛盾せず、誰が何を決めるか、またはそれを決める必要があることが読者向けに整理されている。
- 内容・構造・表現・媒体のレビューを行い、見つけた問題を修正した。
- 未確認の検証や未実施のレンダリングを、完了したものとして報告していない。
